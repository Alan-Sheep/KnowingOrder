## 3. 为什么采用这个排序方法，而不采用替代方法

新增[HybridRetrievalRanking.java](../backend/src/main/java/com/ragqa/rag/retrieval/HybridRetrievalRanking.java)：第26行cosine、第35行rank、第57行fuse。余弦用于比较向量方向，先按最大绝对值缩放再归一化，避免极大数平方溢出或极小数下溢；拒绝空、零向量、非有限数、模型不匹配和维度不一致。

两路融合采用RRF（按名次倒数累加），不直接把关键词分与向量相似度相加。它仅处理已授权编号，不替代权限、版本、资料充分性或引用复核；RRF分数不是答案可信概率。Qdrant可提供向量排序，纯函数的精确余弦排序可作为后续小样本对照，不表示正式问答会先把全库向量读入Java。

例如关键词顺序[10,20]、向量顺序[30,20]、显式smoothing=60，融合结果[20,10,30]；20的分数为2/62，10与30均为1/61，同分按编号升序。这个样例是合成排序验证，不能证明向量模型理解“餐补”等业务词。未把既有“原始优先的改写实验融合”替换成RRF，旧实验边界保持不变。

## 4. 输入输出、问题和处理

| 入口 | 输入与返回 | 边界/异常 |
|---|---|---|
| cosine | 两个TextEmbeddings.Vector → [-1,1]的double | 模型字符串须相同、维度1—2048且非零；坏输入BusinessException code=400 |
| rank | 查询向量、Entry列表、显式阈值、limit → 不可变Similarity列表 | 最多512项，返回1—24范围内的limit；阈值[-1,1]且包含边界；先校验全部再截断 |
| fuse | 两路已排序Long编号、显式smoothing、limit → 不可变Fused列表 | 每路最多24、内部无重复；smoothing=1—1000，保留每路原名次；同分按编号升序 |

512/2048/24是本内核输入保护，60仅为测试传入值，均不是已测得的生产最佳参数或正式空间容量。超512拒绝，不静默只搜索前512项；同编号重复拒绝，避免重复投票；低分或超出top-k的坏尾项也不能被隐藏。输入不改动，结果不可变，无共享排序状态。

模型名称相同不证明权重、分词或预处理一致，后续持久索引仍需绑定模型修订/维度/内容摘要和索引代次。相似片段可能只是主题相关而无法回答原问，不能跳过既有证据判定。真正Qdrant链路还要测试撤回、跨企业、旧索引、部分写入、返回错误编号、超时和写入结果未知，当前没有声称已通过。

### 7.2 为什么选这个方法，而不用别的方法

Qdrant已由用户选定，REST适配器只做创建/核对集合、分批写入、读取核对、范围查询和指定集合清理。官方Java SDK是可替代方案，但本单元只需少量操作，已有RestClient和完整正文时限/响应限额可复用，不为几条协议操作新增依赖。代价是本项目要维护字段契约，因此同时保留故障替身与真实1.19.2契约测试，后续服务升级必须重跑。

默认关闭，只接受127.0.0.1或IPv6回环的HTTP根地址，不接受localhost域名、公网、凭据、路径、查询串或重定向。它符合本轮只部署本机、资料不外发的边界；远端Qdrant需另设TLS、认证、网络与数据许可，不能简单放宽地址校验当作生产支持。

不直接使用rag_chunk.id作为全局向量点编号：确定性UUID还绑定集合、模型修订、企业/空间/文档/版本/代次和片段，避免相同业务编号覆盖其他范围。模型名以外另要求64位十六进制修订摘要；本单元校验其格式和一致性，不声称已从Ollama取得真实权重摘要。

输入Index包含集合名、模型名、修订摘要、维度；Scope包含企业、空间、文档、版本及UUID代次。Point是片段编号、内容摘要和Vector，向量元数据不含原文、密码、令牌或模型回答。上层必须先核权并取得这些可信字段；创建Scope不是完成鉴权。

写入时先校验整批（1—16条、无重复、模型/维度一致、有限非零），稳定归一化后才发送。先GET核对集合的Cosine、维度及schema/model/revision元数据，随后PUT points?wait=true&ordering=strong，只接受completed。模型修订不符返回409，不接管已有集合；create不会覆盖已有集合。

query先核对集合，然后POST points/query；must过滤固定包含enterprise_id、space_id、document_id、version_id、generation、model、model_revision七项。编号以十进制字符串存入payload，避免中间JSON消费者按浮点解析大整数。返回最多24个Hit(chunkId,contentSha256,score)，重核全部定位字段、确定性UUID、摘要、去重及分数范围；任一异常拒绝整份响应，不悄悄采用部分坏结果。命中同分按片段编号排序，但不承诺Qdrant跨top-k边界同分候选完全稳定。

read用相同确定性UUID批量核对，返回Stored(chunkId,contentSha256,vectorSha256)，缺项保持缺项；原始double向量摘要与Qdrant归一化后向量不是同一字节序列。这个入口供未知写结果核对，并不代替“所有批次完整、仍是当前版本、成员仍有权限”的发布判断。

### 7.4 会遇到什么问题，怎样处理

| 场景 | 已实现处理与实际边界 |
|---|---|
| 超时/断连 | 每个公开操作共用min(父任务余额,5秒)，集合核对与后续写入不能各得5秒；连接上限2秒，完整正文256KiB限额。不做应用层自动重试 |
| 写入超时、响应损坏或未completed | BusinessException 503，提示“写入结果尚未确认，请先读取核对，禁止盲目重试或发布索引”；可能已写入，不伪报回滚 |
| 401/403、409 | 权限失败停止调用，不重试、不透传正文；冲突明确409。真实带认证Qdrant部署尚未做，本次权限错误为离线注入 |
| 空结果/集合不存在 | 有效points=[]正常返回空；只有inspect的404返回false，正式查询遇缺集合明确404，不当成“无相关资料” |
| 格式变化/越界编号 | 严格JSON、重复键/尾随内容拒绝、媒体类型检查、范围及点编号重核；上游正文不进入异常信息或日志 |
| 模型更新/错误集合 | schema/model/revision/维度/Cosine任一不符拒绝；新模型必须另建正确集合，完整生命周期仍待实现 |
| double转float32 | 先最大绝对值缩放，再归一化，极大/次正规数仍保留方向；分数边界仅允许1e-6舍入误差，不把相似度当正确概率 |
| 并发/幂等 | 不同范围相同chunkId不覆盖；同范围同输入显式重传仍是同一UUID。尚无同代次冲突写的业务仲裁、多节点发布锁或全局并发限额 |
| 事务/回滚 | 无新增数据库事务；wait=true不是跨MySQL/Qdrant原子事务。部分批次成功后不能发布，持久任务、栅栏与清理策略留下一单元 |

客户端不产生HTTP接口，也没有把底层异常接到新的前端进度中。正式接线时必须在上层服务将“不可用”和“证据不足”分开反馈，并保留原有全局异常与任务终态机制。

## 8. 索引生命周期第一单元：不可变清单与预期点完整核对

### 8.1 为什么先做清单、有哪些替代方案

原客户端可以写入和读取一批点，但不能回答“整个文档版本的预期点是否都核对过”。例如预期17个片段，第一批16个已成功，最后1个未写入；不能用集合存在、第一批completed或总点数达到17来宣布索引可用，因为也可能混入其他版本或错误内容。

先从可信数据库版本快照取得完整片段数、原件摘要及修订，绑定企业/空间/文档/版本/代次、集合/模型/修订/维度，以及每个片段的内容和原始向量摘要，形成不可变预期清单；之后逐批读取全部预期编号。任何缺失或摘要不符都拒绝返回成功核对结果。只记录摘要，不复制原文和向量到清单或日志。

先检索并读取Qdrant官方GitHub仓库qdrant/qdrant-client的qdrant_client/uploader/rest_uploader.py，核对其upload_batch、RestBatchUploader及wait/批次/重试参数。该路径最新提交查询为e50eb17f49851eb710c1f6f502e16cd338898703；本轮读取的是默认分支源码，不将提交查询冒充固定提交全文核验。仅参考分批上传的职责边界，没有复制Python实现或引入SDK。首次沙箱网络认证失败，经许可只读GitHub API成功，未下载文件。

可替代方案是只比较数量或依赖每批写入回执，但两者都不能绑定完整预期内容。官方上传器可替代底层批次传输，企业权限、版本和READY状态仍须由本项目负责。MySQL与Qdrant没有共同的本地事务，核对结果本身不能代替发布事务。

### 9.1 为什么先补这个前置，而不是直接受理任务

### 9.3 会遇到什么问题，当前怎样处理

| 场景 | 当前行为及边界 |
|---|---|
| 服务关闭/模型未配/未安装 | BusinessException 503，提示核对服务或由管理员准备模型，不下载、不悄悄换模型 |
| 模型名相同但修订变了 | 核验前后摘要不同返回409；第二次查不到模型返回503，均不把旧快照交给调用方 |

| 空/重复/损坏/变更后的协议 | 严格JSON、重复键/尾随正文拒绝；重复所选模型、name/model不一致、非法摘要、媒体类型不符均失败。忽略不影响所选模型的正常额外字段 |
| 权限错误、限流、第三方故障 | 任一步302/401/403/404/429/5xx停止，不跟随跳转、不自动重试、不透传上游正文；第二/第三步失败不返回部分结果 |

| 中断/并发 | 调用前、每次发送前及读取后检查预算/中断；保留中断位。中间数据只在方法局部，四路并发不串快照 |
| 事务/回滚/幂等 | 此入口只读元数据，不开MySQL事务、不写Qdrant；任一步失败无本地写需回滚。两次显式调用是两次观察，标签变动时不承诺相同结果 |
| 页面反馈 | 当前没有新增HTTP/前端入口；安全中文异常已准备，后续受理服务接全局处理器/任务终态后才能验收页面提示，不能宣称已在UI验证 |

安全边界：回环地址只限定客户端连接的主机，不证明该主机不会代理远端；元数据检查依赖受控本机服务如实报告。原embed独立调用未在本轮重构，不能因为增加snapshot就声称它已具备修订锁或外发防线。后续执行器需在授权之后核验、执行前后重核、核对向量维度，并配合本机部署禁用云端及网络边界，真实企业资料仍不外发。

两次相同摘要也不能排除核验之间A→B→A变化，或快照返回后标签再次变化。快照不是模型锁，也不是READY发布凭据；worker和最终发布必须重核权限、文档修订、模型身份及清单。若要严格消除此竞态，需要受控不可变模型别名/实例和部署期间禁止替换的机制，而非仅多查一次。

### 9.4 能不能优化，怎样优化、代价是什么

1. **减少元数据请求**：规模扩大后可将只读模型信息按端点/配置模型/摘要短时缓存，但命中缓存仍需核对实际模型修订；模型更新时要失效。代价是失效一致性，不能只缓存模型名后永久复用。
2. **固定执行身份**：使用受控不可变别名或模型实例，禁止索引任务运行期替换；可以减少标签竞态。代价是本机运维规范、模型生命周期与更新流程，摘要字符串本身不能完成锁定。
3. **按真实负载调预算/大小**：安装模型很多或元数据更大时，先采集延迟、响应字节数、并发和内存，再调整5秒/2MiB/256等保护；不能从本次合成快照测试推导上线吞吐。
4. **扩展提供方**：若未来换非Ollama服务，再抽取明确的模型身份接口及相应实现；当前只一个实现，先不新增无调用者的工厂、缓存服务或注册中心。多子清单应先确定执行变体身份再开放，不通过放宽校验冒充支持。

### 11.1 为什么这样做，有哪些替代方案

本单元先核对Qdrant官方GitHub的`qdrant-client/qdrant_client/uploader/rest_uploader.py`：`upload_batch`第18行、重试循环第43行、`wait=wait`第53行及`RestBatchUploader`第78行，文件blob为`75262b6eccb65f59c718d197808be798a8c20371`。只参考分批职责，没有引入SDK或复制重试策略。Web检索无可用正文，GitHub API沙箱认证失败后经平台许可只读核验成功；blob不是发布版本或提交号，未下载文件。

一个节点仅一个执行槽，待处理数据留在数据库；每轮最多读16个候选、成功领取后最多执行一个。多节点靠数据库CAS竞争，不靠Java锁保证全局唯一；单节点忙标记仅防止同一实例的手工轮询与定时器重叠。这不是全局模型并发限制或多租户公平调度。

每次租约取首次任务截止，不续租、不自动重新领取RUNNING；排队和受理已经消耗的时间不补回。相对短租约加心跳，这个方案减少续租线程和暂停竞态，但崩溃后的任务要等首次截止或已设租约到期才终止；首版任务最多120秒。后续若做长任务，须重新设计心跳与写入栅栏，不能仅加大超时。

执行步骤：用任务固定账号/认证版本重建可信身份 → 当前成员编号及显式MAINTAIN → 锁空间/文档，核版本摘要、修订、解析状态和完整数量 → 授权分页取得片段 → 核模型 → 每批最多16条Embedding并重核模型和权限 → 生成完整清单 → 短事务重读片段、持久清单 → 事务外核/建集合、逐批写入 → 全量读取核对 → 再核模型 → 最终短事务重读片段/持久清单/活租约 → CAS到VERIFIED。

实际合成例：企业1、空间401、账号3/成员103、文档501/版本701、修订7，17条“虚构片段0”至“虚构片段16”，模型synthetic:1/摘要a×64/二维。Embedding和upsert各两批16＋1；首次Qdrant写入前MySQL已有完整17行预期。全量两批核对成功才令verified_chunks=17、status=VERIFIED，文档published_version_id仍为空。只有16条实际点或同数量不同摘要均不能成功。

片段读取沿用生产插件每页500的上限，最多两页取得1000条，不申请1000后误信被插件裁剪的结果。校验唯一正编号、从0连续的chunk_index、非空且每条最多1200个UTF-16单元的有效文本；超限、格式字符、非法控制符及孤立代理字符直接失败，不截断。持久清单前和最终核对事务内重读完整片段，防止数量没变但内容被替换。

本轮原件不重新读取；绑定的是数据库版本记录的原件摘要和授权片段快照，不声称重新计算了原文件完整性。内存临时保留最多1000条文本和向量；不是无限流式入库，最大维度2048时仍需按真实堆内存压测。

### 11.3 会遇到什么问题，怎样处理

| 问题 | 当前处理与边界 |
|---|---|
| 跨企业/换账号/停用/撤权 | 每批前后由固定账号重新核成员及显式维护权；ADMIN不隐式拥有知识访问权。失权记录ACCESS_REVOKED，禁止后续写入或成功状态；已发出的HTTP不能因此撤回 |
| 文档变化/同数量换内容 | 检查固定修订、版本摘要、解析状态、实际COUNT；持久清单和最终事务比较完整片段快照，不将数量相同视为内容相同。发布状态DRAFT/PUBLISHED/WITHDRAWN可构建，但不因此成为问答依据 |
| 事务/锁顺序 | 每段5秒事务，READ_COMMITTED，沿用空间→文档→任务/清单顺序；模型与Qdrant调用均无数据库事务。受理的gate不在worker中反向申请；现有片段查询没有独立2秒注解，不能统称每条SQL均2秒 |
| 过期/取消/失租/中断 | 全链路共享首次截止余额，外部单次仍最多5秒，不按批续时限。取消/失租后不再发下一批或VERIFIED；关闭/中断保留中断位。时钟回退安全停止，数据库时间约束可能使回写延后，不能保证任意阻塞下准点强杀 |
| 模型换版/服务不可用 | 推理前、每批后、最终再读模型元数据；修订/维度变化MODEL_CHANGED，不可用VECTOR_UNAVAILABLE；空、数量错误、非有限/零向量不进入清单。无下载或自动重试 |
| 清单保存失败 | 清单行与任务总摘要同事务回滚，首次外部写次数为0；原有部分清单不接管、不删除重写。清单先前已提交但最终状态失败时保留追溯 |
| Qdrant创建/写入未知 | WRITE_UNCONFIRMED并停止，不自动补写、重试或回放RUNNING；已写点和完整预期均保留。本单元选择保守终止，不实现自动读取恢复未知写；后续人工核对或经授权新UUID/新generation重建 |
| Qdrant读取失败/缺点 | 不可用是VECTOR_UNAVAILABLE，缺点/摘要冲突是MANIFEST_MISMATCH；不会用成功子集反算完整数量，不把故障当成“无资料” |
| 提交失败或回执丢失 | 最终事务内错误回滚VERIFIED；实际提交后丢失回执时fail只匹配活RUNNING，不覆盖已提交VERIFIED、取消或超时。下一轮不自动重放已结束任务 |
| 存储宕机/异常日志 | 状态保存失败时不伪造成功，后续轮询仅清理或查询原状态，不重放RUNNING。调度故障只输出固定脱敏提示并抑制连续重复；业务失败存白名单分类，无SQL、原文、密钥或上游正文日志 |
| 页面及监控 | 复用已有Java任务状态/安全中文message，但没有新增HTTP/UI入口，不能说前端已可使用。持久状态和调度提示不等于已完成指标、告警和生产运维监控 |

安全限制仍存在：本机回环并不能证明服务不代理远端；模型前后快照不能消除A→B→A或检查后替换，必须配合受控模型实例/不可变别名和部署网络边界。权限在HTTP发出前后复核，不是跨MySQL和模型服务的原子授权事务。

清单核对比较Qdrant payload中的预期摘要，不重新验证实际向量数值、无额外点或全局原子快照；VERIFIED仍不是READY。失败代次未自动清理，不能为了清理一个文档删共享模型集合。真实企业原文外发、中转模型和公开搜索均未增加授权。

### 11.4 后期可以怎样优化，代价是什么

1. **吞吐与公平**：实测模型批耗时、排队、数据库锁和堆内存后，按模型设跨节点并发与企业公平队列；不能简单加线程，否则会放大CPU/内存、连接和第三方写入压力。
2. **大文档**：可将中间向量按有界批次放私有暂存、流式累计完整预期，封存后再写Qdrant；代价是临时数据权限、回收、摘要协议与恢复一致性。当前1000/1200/2048是保护边界，不是生产容量证明。
3. **降低复核开销**：在不可变版本和片段写入协议得到实库证明后，可持久片段集摘要减少整表重读；代价是所有写入口都必须维护摘要，不能直接删掉最终比较。模型元数据缓存同样需修订失效策略。
4. **未知写恢复**：未来可按已持久预期只读核对未知批，完全一致再继续；部分存在时仍不能盲目重放。还需处理旧worker迟到写、跨进程租约和清理，不能把客户端wait=true当成跨库事务。
5. **发布与检索**：下一单元实现MySQL授权READY指针、代次切换/撤回和读取复核，再接RRF混合检索。发布前须重核来源、模型、权限和完整清单，保留旧代次安全回退；本轮没有提前实现这些能力。
