# 会话业务单元说明

## 单元一：服务层归属读取

完成日期：2026-10-17。天气、拒答状态和黄金集质量问题按最新用户指令保留待办，继续业务。本单元只建立会话读取归属边界，不表示登录或对外会话功能完成。

### 一、为什么这样做，不用其他方法

消息、历史和任务都要关联会话，后续不能在每个Controller里各写一遍归属判断。采用 `ConversationService` 接口和 `service.impl` 实现，符合已有服务分层约定；通过既有Mapper在一次查询中同时限定会话编号和当前用户编号。

不采用“先按会话主键读取完整数据，再在Controller比较用户”的方式：容易有入口遗漏比较，也会提前把其他用户的数据载入业务流程。不区分“资源不存在”和“属于其他用户”的提示，避免借错误信息探测他人的会话是否存在。

本次复用MyBatis-Plus参数绑定与现有逻辑删除映射，没有额外依赖、数据库变更、认证框架选型或缓存。单次只读查询不增加事务；未来跨步骤写入再定义原子性和回滚边界。

方法输入为 `Long currentUserId, Long conversationId`，返回 `RagConversation`。当前用户编号必须来自未来服务端认证结果；正整数并非登录证明，不能用请求JSON的userId或模型输出代替身份。本单元尚无Controller调用方，不能通过用户传两个编号来对外提供查询。

已执行固定样例：输入用户77、会话42；模拟Mapper返回 `{id:42,userId:77}`。测试用真实映射验证SQL同时含 `id = ? AND user_id = ?`、`deleted=0`，绑定值依次为42、77，再断言服务返回同一会话。Long.MAX_VALUE也作为合法Java编号验证，值不拼入SQL。这里的行数据来自测试替身，不冒充真实MySQL查询。

无匹配行时抛 `BusinessException`，code=404、message=“会话不存在或不可访问”；用户或会话编号为空、零或负数时code=400，且不调用Mapper。数据库异常继续向上传递，由既有异常边界处理；不能将数据库不可用说成资源不存在或读取成功。

### 三、可能遇到什么问题，怎样处理

- 参数注入：编号为受限类型并使用Wrapper绑定，不拼接SQL，也不靠替换引号。测试检查真实SQL只有两个编号参数，且归属条件与主键条件为AND。
- 逻辑删除遗漏：复用 `SoftDeleteEntity.@TableLogic`，测试检查生成SQL确实包含 `deleted=0`；未额外编写绕过逻辑删除的原始查询。
- 并发条件串用：每次调用新建Wrapper，服务不保存当前用户、会话或查询条件。20组读取并发执行，逐一检查回填编号与用户一致。
- 数据库故障：不捕获后返回null或404，也不新增无限重试；该单次查询没有写入副作用。
- 未来先查后写竞态：读取通过后会话仍可能被删除或状态变化。后续更新、删改、消息写入须用各自的归属条件和事务策略；本方法不能为另一次写入担保。
- 身份伪造：本单元不解决登录。正式HTTP接入前必须有可信身份来源及越权测试，不得把接口参数userId视为授权依据。

### 四、能否优化，怎样优化

现有会话主键已限定单行，暂不增加索引或Redis缓存；没有性能证据时增加归属缓存会带来删除、封禁和身份变化后的失效风险。后续列表按用户过滤、历史按会话分页时，再以查询计划和实测评估索引及缓存。

后续对外响应使用明确DTO，列表限制页大小，历史限制内容规模。服务接口只约束读取；用户是否禁用、身份是否过期及写事务规则分别由后续认证和业务单元处理。

## 单元二：认证主体契约与当前账号复核

完成日期：2026-10-17。本单元建立认证成功后的业务衔接契约，尚未实现登录、密码或凭据验证，也没有对外接通会话接口。

### 一、为什么采用稳定用户主键

服务端认证成功后，使用只含用户主键的不可变 `AuthenticatedUserPrincipal`，由 `CurrentUserService` 复核账号仍正常且未删除，再把编号交给会话归属服务。不根据用户名重新推导身份，避免后续改名或名称重新分配时改变已绑定账号；也不解析普通Principal名称中的数字来猜测用户。

此处不另建ThreadLocal：身份作为参数明确传递，每次查询新建条件，不在线程或服务字段中保存当前用户。ThreadLocal不能代替身份认证或资源归属，后续若认证框架管理线程上下文，再由适配层提取本项目主体；不会因换线程就默认获得用户身份。

### 二、代码与数据怎样调用

| 文件和方法 | 作用 |
|---|---|
| backend/src/main/java/com/ragqa/domain/dto/AuthenticatedUserPrincipal.java：构造函数、getName | 不可变身份只含正整数用户主键；名称是该主键的字符串，不保存密码、令牌或用户名 |
| backend/src/main/java/com/ragqa/service/CurrentUserService.java：requireUserId | 声明只接收服务端认证成功后建立的本项目主体；拒绝其他Principal类型 |
| backend/src/main/java/com/ragqa/service/impl/CurrentUserServiceImpl.java：requireUserId（26行） | 绑定id、正常状态查询，只选id；复核结果编号与主体一致，返回Long |
| backend/src/main/java/com/ragqa/common/ResultCode.java：UNAUTHORIZED（18行） | 仅追加业务码401及固定安全提示，不改变旧错误码与现有异常处理行为 |
| backend/src/test/java/com/ragqa/service/CurrentUserServiceTest.java | 21项离线验证，包含真实生成SQL、错误主体、编号错配、异常及并发隔离 |

计划接入顺序为：实际认证验证凭据 → 认证适配层创建 `AuthenticatedUserPrincipal` → `CurrentUserService.requireUserId(principal)` → `ConversationService.requireOwned(userId, conversationId)`。目前前两步以及HTTP调用方尚未实现，不能把这条计划流程当作已跑通登录。

已执行固定样例：服务端测试主体为 `new AuthenticatedUserPrincipal(77L)`，Mapper替身返回id=77，结果为77。真实映射生成 `SELECT id FROM sys_user WHERE deleted=0 AND (id = ? AND status = ?)`，绑定77和正常状态0；测试断言没有选取用户名、密码散列、邮箱或昵称。查询结果若为88，必须拒绝，不能把身份改为88；普通 `Principal` 即使名称为“77”也拒绝且不查询。

### 三、问题与故障怎样处理

- 主体缺失、类型不支持、账号不可用或返回编号错配：统一抛 `BusinessException`，业务码401、提示“请先登录或登录已失效”，不透露账号是否被禁用或删除。
- 无效认证主键：值对象构造阶段拒绝0、负数；合法Long大值不截断。此类非法构造属于服务端适配错误，不能通过前端传参伪造主体。
- 数据库故障：向上传递，不误报未登录，不授予默认用户、不自行无限重试。复核只保证查询时点的账号状态，后续写操作的竞态与事务仍须另行处理。
- SQL与敏感数据：参数化绑定编号和状态；查询投影仅id，不加载完整账号，不输出主体、密码或令牌日志。
- 并发：20组主体并发解析分别返回自己的编号，查询条件不共享；该结果不代表已经完成生产容量或跨请求任务测试。
- 保留失败证据：初稿按普通Principal名称查用户名，原39项测试通过，但新增反例 `untypedPrincipalCannotBecomeAnAuthenticatedUser` 单独执行时失败，实际没有抛预期异常。随后改为明确主体类型与稳定主键，保留该反例，再补编号错配等断言；最终42项通过，不通过删除反例或降低断言掩盖问题。

### 四、优化与当前边界

认证主体类型本身不是密码、签名或登录证明：服务端仍须先验证凭据再创建它，禁止将客户端JSON、自定义用户头或请求参数直接绑定为可信主体。后续认证框架若提供包装主体，必须先验证认证状态，再由适配层提取或建立本项目主体；不得盲目强转或根据getName猜测身份。

当前按主键每次复核，不缓存账号可用性；账号禁用与删除不会被本单元的缓存继续放行。以后如有性能证据，再设计失效机制和时效边界。登录过期、会话撤销、退出、CSRF、限流和HTTP401响应由后续认证单元实现。本次新增的是业务码401；现有GlobalExceptionHandler仍将业务异常包装为HTTP200 + Result.code，不能把两者混淆，也不能据此宣称HTTP鉴权已完成。

## 单元三：访客与账号的生命周期及额度约束（设计记录）

记录日期：2026-10-17。用户选择访客优先、保留账号登录，并补充访客每日次数或token耗尽后需要登录。本单元仅固化业务边界，覆盖上一节“下一单元先做账号登录”的安排，不代表认证、额度或清理已经实现。

后续规则修订：本节原先“午夜立即结束在途任务”的约定已被下文单元五覆盖。北京时间00:00停止旧身份受理新问题，已受理任务沿用原截止时间限时收尾并提供有限结果阅读期；当前未实现。下列相关说明已同步调整，避免把初版方案作为当前验收依据。

### 一、为什么采用两种身份与当日日切

访客降低首次使用门槛，账号承载长期历史；两者保留期不同，不能让所有用户共用匿名账号，也不能让访客编号碰巧命中sys_user记录。现有AuthenticatedUserPrincipal和CurrentUserService保留账号语义，下一实现单元需明确访客主体及归属存储，不能仅把未登录用户放行。

按平台北京时间的次日00:00停止旧身份受理新问题，而非访问后24小时。示例：2026-10-17 23:59:30访问，10月18日00:00进入日切；如有已受理任务，则保持原截止时间有限收尾，不立即掐断等待。修改前端为纽约时区不延长期限。此为规则样例，尚无运行代码或测试结果。

只限定问题次数不能约束一句多问及多阶段调用的费用，只限定token又不易向用户解释，因此同时设置次数和累计token上限，任一耗尽后引导登录。具体数值待实际消耗基线确认，不把示例值写成生产承诺；账号也保留独立额度和全局上限。

### 二、计划怎样传递身份、时间和额度

计划链路：建立或验证服务端访客身份 → 检查expiresAt → 校验资源归属与输入 → 按幂等标识原子预占次数和token → 可靠接纳任务 → 各次模型调用前核对预算 → 依可信usage结算 → 返回答案和余额摘要。业务会话编号只能定位资源，不能代替凭据或决定用户身份。

一次受理的用户原始提交计一次，拆分的子问题共享该次受理关系；规划、评估和生成的模型调用均累计计入token。搜索额度单独控制。参数错误、接纳失败不算提问，重复提交不重复预占；后续补充消息作为独立受理时另计次数，不因合并任务而漏计已发生消耗。token不是字符数，现有返回文本的调用契约尚不等于已有usage记账能力，后续需在供应商适配层和账本单元补齐。

日切与最终到期使用服务端时间分别判定；零点前任务可在原时限内收尾，结果阅读期及整个收尾期有硬上限，刷新、重连和页面常开不续期。前端先告知临时保存规则，日切后保留获准任务及必要上下文，最终到期清除对应正文，不重新提交原问题。账号退出或会话失效不触发历史日切删除。现有SQL的expires_at_epoch_ms尚不足以代表这些不同期限，字段扩展留待下一存储单元。

### 三、会遇到的问题及验收要求

- 日切清理与安全访问分开：收尾期仅允许已受理任务及必要上下文，最终到期或撤销立即阻断，清理停机不扩权。物理删除分批、有界重试并监控积压，不能只删除Cookie或软删除会话，也不能误删仍获准收尾的数据。
- 跨日写回：保留原任务时限与受理日预算，超时后停止后续调度并尝试取消；持久化和缓存写回再次校验归属、任务范围和期限，清理与迟到结果不得互相复活数据。已发生的供应商费用不能按本地取消结果全部退款。
- 额度竞争：采用原子预占和幂等结算，验证最后一次机会的并发竞争、多子问题预算、重复回调、数值溢出、事务回滚及计量存储故障。不能用“先查余额再无条件扣减”或依赖前端禁用按钮控制成本。
- 结果未知：usage缺失、异常或超时不能记为零，后续账本需定义保守预占、有界对账与释放，防止无限挂账或重复扣减；存储不可用不绕过额度发起新付费调用。
- 新身份绕额度：刷新和新建会话不重置当天额度；清Cookie、无痕访问仍需网络来源与全局限制，IP不能精确识别自然人，要测试共享网络误伤。防滥用计量数据与聊天正文分开保留，凭据及原文不得进入账本、日志或指标。
- 清理范围错误：访客和账号即使编号相同也不能互读或误删；账号历史不进入访客清理条件。账号登录后是否迁移访客历史留待独立确认，不能自动把旧数据永久保存。
- 必测边界：固定时钟验证午夜、跨月跨年和闰日；覆盖设备时间伪造、展示时区切换、多窗口、重启、重连、到期与结算竞争、数据库异常和清理失败。用户提示须结束等待，区分自身额度不足与第三方故障。

### 四、优化方向与当前边界

先设计最小身份和归属存储，再接签发、过期、额度、会话接口及清理；按各独立概念实施和验证，不为本次文档改动提前安装Redis或认证框架。后续多实例需要共享计量及原子竞争规则，不能依赖某台机器的内存计数；是否采用MySQL或Redis在对应单元按一致性与成本讨论。

访客当日清理规则优先于旧的任务结果24小时提案；账号历史继续独立保留。没有执行数据删除、修改表结构、前后端业务或既有通用设施；本轮仅做文档一致性和编码检查，不运行数据库、模型或搜索，也不沿用旧测试数量宣称本轮通过业务验收。

当前位置：会话归属与账号复核服务已存在 → 本单元记录访客/账号、日切与额度规则 → 下一步评审身份和归属存储的最小改动 → 分步接入访客访问、额度、历史与清理 → 后续补账号登录及临时历史转存策略。天气、拒答状态和质量基线继续后置，仍为上线前缺口。

### 一、为什么采用独立访客表与二选一归属

建议保留sys_user作为正式账号，新增rag_guest_identity保存短期访客身份。rag_conversation保留user_id，新增guest_id，并约束两者恰好一个非空；rag_message继续通过conversation_id关联，不重复保存归属信息，不建物理外键。

不使用共享匿名账号或往sys_user写假用户名、假密码：访客没有账号密码，保留期也不同。暂不改为owner_type加owner_id：会重命名现有user_id并迁移账号数据，而二选一字段能够保留既有账号编号与索引。代价是未来增加第三类主体要再评审；当前只有访客和账号两类，不提前设计通用权限系统。

### 二、字段、SQL与调用关系

| 字段或约束 | 含义与调用位置 |
|---|---|
| rag_guest_identity.id | 服务端内部主键，只用于归属，不能作为认证凭据 |
| credential_hash | 唯一的凭据摘要，拟保存SHA-256的32字节结果；不存原始凭据，不序列化或写日志 |
| issued_at_epoch_ms / expires_at_epoch_ms | 当前首批SQL的UTC毫秒字段；原按北京时间次日零点设计，尚未执行。单元五新增有限收尾规则后，日切、最终失效与阅读期限须分开评审，不能直接用原字段覆盖全部期限 |
| revoked | 0有效、1已撤销；即使未到午夜也能主动禁止身份使用，不与会话软删除混用 |
| idx_guest_expiry | 按到期时间分批扫描访客；扫描仍需容量限制，不等同自动清理 |
| rag_conversation.user_id / guest_id | 分别逻辑关联sys_user.id与rag_guest_identity.id；CHECK约束禁止同时有值和同时为空 |
| idx_guest_id | 按访客列出会话并定位其待清理数据，原idx_user_id保留 |

面向已有库的一次性增量结构如下，实际文件为backend/sql/migrations/20261017_01_guest_identity.sql；不是初始化脚本，不得重复执行或加入启动自动建表流程。CHECK约束的实际强制执行能力须核对目标MySQL版本，要求8.0.16及以上；创建与变更是分别执行的DDL，不承诺普通业务事务能够整体回滚。

```sql
CREATE TABLE rag_guest_identity (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '访客内部主键, 不作凭据',
    credential_hash BINARY(32) NOT NULL COMMENT '凭据SHA-256摘要, 禁止返回或记日志',
    issued_at_epoch_ms BIGINT NOT NULL COMMENT '签发时刻, UTC毫秒',
    expires_at_epoch_ms BIGINT NOT NULL COMMENT '到期时刻, UTC毫秒',
    revoked TINYINT NOT NULL DEFAULT 0 COMMENT '撤销标记: 0未撤销 1已撤销',
    PRIMARY KEY (id),
    UNIQUE KEY uk_guest_credential_hash (credential_hash),
    KEY idx_guest_expiry (expires_at_epoch_ms),
    CONSTRAINT chk_guest_lifetime CHECK (
        issued_at_epoch_ms >= 0 AND expires_at_epoch_ms > issued_at_epoch_ms),
    CONSTRAINT chk_guest_revoked CHECK (revoked IN (0, 1))
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_unicode_ci COMMENT = '当日访客临时身份';

ALTER TABLE rag_conversation
    MODIFY COLUMN user_id BIGINT UNSIGNED NULL DEFAULT NULL COMMENT '账号归属, 与guest_id二选一',
    ADD COLUMN guest_id BIGINT UNSIGNED NULL DEFAULT NULL COMMENT '访客归属, 逻辑关联rag_guest_identity.id',
    ADD KEY idx_guest_id (guest_id),
    ADD CONSTRAINT chk_conversation_owner CHECK (
        (user_id IS NOT NULL AND guest_id IS NULL)
        OR (user_id IS NULL AND guest_id IS NOT NULL));
```

目标归属样例：会话42保存user_id=77、guest_id=NULL；会话43保存user_id=NULL、guest_id=77。后续服务须保证账号77与访客77不能互读，目前未实现该访客查询入口。迁移后已有账号会话的guest_id为NULL，保留原归属；NULL/NULL及77/77两种归属应被数据库拒绝，尚待真实MySQL验证。CHECK只保证形状，不能证明对应身份存在或有效，仍由service复核并处理写入竞态。

接口规划：账号继续使用CurrentUserService.requireUserId及现有requireOwned(Long, Long)。访客采用独立的AuthenticatedGuestPrincipal和GuestIdentityService，由服务端验证凭据、摘要匹配、撤销及到期后建立主体；后续增加requireOwned(AuthenticatedGuestPrincipal, Long)读取入口，按会话id、guest_id及user_id为空联合过滤。构造主体或编号为正本身不是认证证明，访客入口仍须复核存储有效期，不接受客户端直接绑定主体。

写操作不只依赖先读归属：会话创建、消息写入、额度预占和清理需在各自事务中复核身份，并在相同访客记录上采用一致的锁顺序或条件更新规则，防止清理与写回相互复活数据。任务和额度账本另行设计，不能用rag_message.token_count充当全部规划、评估及失败调用的账本。

### 一、设计意图与取舍

把新问题受理期限、任务执行上限、结果阅读期限分开。仅增加“是否在线”无法表达权限，单个到期时间也无法兼顾零点停止接单和原任务继续执行。建议状态字段配合固定时间边界，权限判断始终复核服务端时间、可信身份和具体任务；状态不是定时器，扫描任务漏跑不能导致ACTIVE无限放行。

保留首次迁移脚本20261017_01_guest_identity.sql作为第一版结构，在下一批新增第二份迁移，不回写已经交付的第一份脚本。初始化schema同步表达最终结构；已有库按迁移顺序处理，空库只执行最终schema。此次不增加额度账本表，匿名额度主体及其可信凭据是另一个独立概念，后续评审，不能先用guest_id冒充每日额度主体。

### 二、已生成的字段与后续权限计算

SQL中的rag_guest_identity继续保留id、credential_hash与issued_at_epoch_ms，作以下调整，时间均为服务端确定的UTC毫秒：

| 字段 | 具体含义与约束 |
|---|---|
| status | TINYINT；0=ACTIVE、1=REVOKED、2=DRAINING、3=EXPIRED。由原revoked改名扩展，保留旧0/1含义，避免两个字段分别表达撤销而不一致；有效值需CHECK约束 |
| accept_until_epoch_ms | 本身份所属北京时间业务日的次日00:00；now等于该时刻就不能再受理新问题，不因刷新或读取更新 |
| drain_until_epoch_ms | 该身份已受理任务的固定执行总上限；签发时按日切时刻加当时允许的最大任务时长确定，受理前确认具体任务原deadlineAt不超过它；日切后不再受理新任务 |
| expires_at_epoch_ms | 继续保留原字段名，表示身份最迟失效的硬上限；新身份按drain_until加结果阅读窗口确定，不代表其间可读取全部历史或保证活到该时刻 |
| result_read_window_ms | 签发时保存的结果阅读窗口，后续配置变化不延长旧身份；已确认开发初值10分钟，SQL默认600000毫秒，旧记录迁移为0；Java签发与运行配置尚未实现 |

时间形状约束建议为0 <= issued_at < accept_until <= drain_until <= expires_at，阅读窗口非负；新签发身份要求正的阅读窗口，并校验时间加法溢出。索引暂复用expires_at上的到期索引，根据实际扫描查询再评估status/时间联合索引，不提前堆叠索引。

计划权限规则：

- 新提问：可信凭据有效、status为ACTIVE、now < accept_until、采用新签发规则且阅读窗口为正，并且额度原子预占成功，才允许受理；任一条件不满足就拒绝旧身份接单，不能只看status。
- 原任务执行：凭据未撤销、归属匹配、任务已在accept_until之前可靠受理，且未终结；截止仍采用原deadlineAt，受理时保证其不晚于drain_until。收尾期只允许必要后续调用与原预算，不能新增子任务、扩大问题或重新计时。
- 原结果读取：只允许获准收尾任务及必要上下文；终态结果到期时间取finishedAt加result_read_window与身份expires_at的较早者，并固定保存。每次查询检查now严格小于该期限，不在读取时重新起算。
- 状态迁移：ACTIVE在日切时根据受保护任务进入DRAINING或EXPIRED；DRAINING在所有受保护执行/阅读记录结束或硬上限到达后转EXPIRED；ACTIVE和DRAINING可转REVOKED。EXPIRED、REVOKED均不能转回ACTIVE；没有可信任务记录时不凭页面心跳授予收尾权限。
- 多任务：任一任务结束不直接废弃身份，应核对其余受保护记录。任务完成、日切与清理采用同一访客记录协调和条件更新，防止重复完成或并发清理使状态回退；具体事务实现另行单元验证。

### 三、预期样例与兼容边界

以下为设计计算示例，并非运行结果：假设访客签发时任务时长上限90秒、结果阅读窗口10分钟，2026-10-17所属身份的accept_until为10月18日00:00:00，drain_until为00:01:30，expires_at为00:11:30。23:59:40受理任务时，其原deadlineAt为00:01:10；若00:00:20完成，该结果到期为00:10:20。刷新、重连或同页再提问不改变这些已保存的期限。没有待保护任务时，不因硬上限还未到而开放旧历史。

如果将来调大任务配置，新受理任务也必须符合当前身份已经保存的执行上限；必须在受理前确定最终预算或拒绝接纳，不能受理后偷偷截短承诺，也不能延长既有身份。用户新一天的提问使用新访问身份及当天账本，原任务维持原归属，切换不能串读。

第二份迁移应保留旧身份的原到期边界，不自动给历史记录补发收尾或阅读权限：旧expires_at可作为新增受理/执行边界的保守映射，旧阅读窗口记为0，并保留原撤销0/1值。窗口为0的迁移记录不再接纳新任务，也不能凭它推算新的结果期限，已有记录只按原授权期限处理；新任务须由服务端按新规则签发身份后接纳。执行前若发现已有访客记录、在途任务或不匹配结构，须核对部署和数据状态后评审，不凭本项目尚无访客服务就断言实际库为空。DDL不提供普通事务整体回滚保证，不执行删除或自动重签。

现有TaskSnapshot的expiresAt仍表示单个终态结果的读取期限，不应直接填身份总上限；TaskDeadline仍代表原任务预算，不因日切重建。任务与身份的关联、持久化、幂等受理、原子预算及截止执行机制仍未实现，本批不修改这些Java契约。
