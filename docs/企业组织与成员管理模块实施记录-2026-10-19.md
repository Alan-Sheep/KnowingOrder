# 企业组织与成员管理模块实施记录（2026-10-19）

本轮按完整业务模块交付。平级部门治理、企业成员分页、管理员开户及直属部门/成员状态调整已接通Java、Vue和开发MySQL；不需要新表或迁移，没有新增依赖。以下区分代码、离线、真实开发库和生产验收，不把本机成功等同上线完成。

## 1. 范围、为什么这样做以及替代方案

账号表示登录身份，企业成员表示这个账号在某个企业的角色、部门与状态。复用sys_user、sys_enterprise、sys_enterprise_member、sys_department及rag_knowledge_grant，不将企业身份塞回账号表，不建立物理外键；跨表归属由服务端管理事务及资源查询验证。

| 本轮选择 | 为什么选它 | 替代方案及暂不采用的原因 |
|---|---|---|
| 平级部门、每成员一个可空直属部门 | 与既有成员和部门授权模型一致，能独立验证调岗、停用与撤权 | 部门树/多部门会新增继承、例外和祖先变化的权限规则，当前不扩展 |
| 有效企业ADMIN管理，知识读取仍要求明确空间授权 | 防止组织管理权变成私有知识或他人会话读取权 | 仅靠前端隐藏按钮不能挡直接请求；ADMIN全放行违背现有资源边界 |
| 行锁下重新核权，版本条件更新 | 同时处理执行期间撤权与两个管理员覆盖旧数据 | 单纯先查后写有竞态；仅乐观版本不解决关联检查与身份状态变化 |
| 部门停用前清空全部成员及有效部门授权 | 不代替管理员决定成员去向，也不隐式修改多个空间的授权 | 自动迁移/级联撤权会扩大写入范围，且重新启用可能恢复意外权限 |
| 复用企业权限版本记录部门变化 | 所有既有敏感读取和任务都能拒绝旧快照，减少漏接失效路径 | 单独组织版本更精细，但需要新字段和逐路径失效评审；本轮不增加 |
| 复用Session、CSRF及既有开户服务 | 已有认证、口令编码和统一异常设施可以直接使用 | 不新增JWT、公开注册、SSO或完整IAM平台，避免并行维护认证体系 |

**重要代价**：部门创建、改名、启停都会递增企业权限版本，可能使该企业无关的在途知识任务也因旧快照失效而结束。读写组织均复用会锁企业、账号、管理员成员的查询，属于保守串行化，不是精细失效或高并发优化。成员状态与直属部门修改只递增目标成员权限版本。新接口不允许管理ADMIN，不新增角色变更、密码重置、删除或部门树。

## 3. 接口与数据如何流转

组织根路径为`/api/enterprises/{enterprise}/organization`。所有正常业务响应仍为Result<T>，业务异常走BusinessException与既有GlobalExceptionHandler；404不区分目标不存在和无管理权，409表示旧版本、同名或关联未清理，400表示非法输入。HTTP状态和Result.code均须检查，不能仅凭HTTP 200当成功。

| 方法与相对路径 | 输入与成功结果 |
|---|---|
| GET /departments | pageNum默认1、pageSize默认20；返回enterprisePermissionVersion和部门分页page |
| GET /members | 相同分页参数；返回成员分页page，含账号状态但不含哈希、认证版本或口令 |
| POST /departments | name、数值expectedEnterpriseVersion；返回新部门和递增后的企业权限版本；禁止携带status |
| POST /departments/{id} | name、数值expectedEnterpriseVersion、整数status=0/1；无变化不递增版本 |
| POST /members/{id} | 数值expectedVersion、明确提供的departmentId、整数status=0/1/2；返回成员新版本 |
| POST /api/enterprises/{enterprise}/employees | 复用已有开户入口，username/password；返回userId/memberId/enterpriseId，不默认授权知识空间 |

部门名称strip后1—128个Java UTF-16单元，拒绝控制符与换行；前端也校验，但服务端为准。部门编号必须为正整数Long字符串；清空部门必须显式JSON null，遗漏departmentId拒绝。版本必须是正整数JSON数值，拒绝字符串、小数和布尔的隐式转换。后端分页每页1—100、页码1—100000；前端每页20。限制分页规模不表示深页查询已具备生产性能。

实际真实页面运行在企业1：创建部门1、开通员工成员12（账号36），用户名`org-test-1792391328887`。成员先分配部门1，部门停用因仍有成员被拒绝；随后清空该成员部门并停用，再把部门改名加“归档”并停用。两种最终status均为1，成员departmentId为null，记录保留，既有员工/部门未修改；口令随机临时生成，不保存或输出。

例如成员保存请求为`{"expectedVersion":1,"departmentId":"1","status":0}`；响应中的成员编号、账号编号和部门编号为字符串，permissionVersion递增为2。使用旧expectedVersion再次提交会得到409，不覆盖较新调整。该行为由隔离测试断言并经真实页面分配/读回验证，真实同版本并发尚未演练。

事务先requireMember取得可信快照，再findActiveMemberForUpdate锁定并比较原快照。写入目标必须同企业；部门必须有效；目标成员必须是EMPLOYEE。部门修改和企业版本递增同事务，版本更新失败整体回滚。停用成员不是删除账号，也不是抹除原空间授权；重新启用可能恢复其既有明确授权，页面必须让管理员确认。

## 4. 会遇到什么问题、现在怎么解决

| 问题/反例 | 当前处理与验证边界 |
|---|---|
| 前端把enterprise或member改成别人的编号 | 服务端ADMIN与企业范围SQL强制校验；跨企业/成员/非ADMIN在H2和HTTP断言，真实多角色矩阵待验 |
| 请求开始后管理员被停用或权限版本变化 | 事务内锁定并复核原身份快照，失败拒绝；不只信Session中的旧角色 |
| 两位管理员同时调岗覆盖数据 | expectedVersion与条件UPDATE，旧版本409；H2并发一胜一409，真实MySQL并发/死锁待验 |
| MySQL普通SELECT读旧快照，漏看刚提交成员或授权 | 关联存在性检查使用LIMIT 1 FOR UPDATE当前读；同时要求相关管理写路径遵循已有企业锁协议；H2不证明MySQL隔离与锁顺序 |
| 部门停用顺便造成成员/授权丢失 | 有任意关联成员（包括停用/离职）或有效部门授权就拒绝；不自动搬人/撤权；回滚断言保留原名称和版本 |
| SQL字符、HTML或控制字符进入名称 | MyBatis #{}绑定数据，固定SQL；Vue文字渲染，不用v-html；不靠替换引号“防注入”；控制字符在入口拒绝 |
| 超时/网络断开时后台其实已提交 | 页面标记结果未知、暂停继续写入，刷新核对本轮名称/账号；不自动重试，也没有宣称创建接口实现了UUID幂等 |
| 口令或组织资料被日志/页面缓存保存 | NoPayloadLog、Mapper INFO、返回字段白名单；提交/卸载清空口令，不写浏览器存储；自动化检查退出清理 |

管理事务设置5秒；前端每个客户端操作默认10秒且包含其CSRF请求，无自动重试。组织刷新先后读取两种分页，各有自己的10秒预算，因此整个刷新最坏可能接近20秒，写入后刷新还包含写入那一次操作。收尾发现原提示“最多等待10秒”易被理解为整次页面动作，已精确改成“各接口操作最多等待10秒，刷新会依次读取部门和成员”；本轮未实现跨接口共享总时限。事务timeout也不承诺强制终止所有阻塞JDBC或网络I/O，上线需结合驱动、连接池、数据库锁等待和HTTP超时验证。

## 6. 优化方向、知识点与接续边界

| 出现什么瓶颈再做 | 具体候选方法 | 代价与必须补的验证 |
|---|---|---|
| 组织列表锁等待、管理员互相阻塞 | 先测管理SQL与锁等待，再评审读路径双次核权或更小范围锁 | 防止撤权窗口、锁顺序改变及列表快照混合；必须用真实MySQL并发测，不先缓存绕过核权 |
| 改名也导致大量知识任务旧快照失效 | 独立组织修订与权限修订，纯展示变更不递增权限版本 | 新字段/迁移，全部读取、受理、worker、引用失效路径需逐一覆盖，不能只改新Controller |
| 深页/OFFSET和COUNT耗时上升 | 按企业和主键游标分页，结合EXPLAIN评审现有复合索引 | 接口/前端翻页契约改变，撤权与增删期间的稳定顺序、总数语义需重新定义 |
| 组织规模大、操作需要审计 | 独立管理事件记录与审批/批量预览，必要时异步导入 | 需要保留期、脱敏和授权；当前请求追踪日志不是完整审计台账 |
| 创建回执丢失人工核对负担高 | 请求UUID与服务端结果绑定，评审唯一名称约束及冲突规范 | 同事务持久幂等记录、失败/提交未知与重放测试；当前版本控制不等于创建幂等 |
