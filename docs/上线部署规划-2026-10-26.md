## 二、为什么不是 2 GiB

这个项目没有用 Redis（`redis/` 仅 README 占位）、没有接 Qdrant 和本地 Embedding（`KNOWLEDGE_QDRANT_ENABLED` / `KNOWLEDGE_EMBEDDING_ENABLED` 默认 `false`），模型与搜索都走外部 API，所以**不需要 GPU、不需要大内存跑模型**。但即使这样，一台机器上仍要同时装三样东西：

| 组件 | 常驻内存（估算） | 说明 |
|---|---|---|
| MySQL 8.0 | 450–550 MB | `innodb_buffer_pool_size` 调到 256M 后 |
| Spring Boot（JDK 17） | 750–900 MB | `-Xmx512m`，含 Metaspace、线程栈、直接内存 |
| Nginx | 30–60 MB | 静态文件 + 反代 |
| 系统 + sshd + 监控 | 200–300 MB | Alinux 3 正常水平 |
| **合计** | **1.4–1.8 GB** | 稳态 |

稳态已经吃掉 2 GiB 的 70%–90%。真正的问题在**峰值**：文档解析是 `@Async` 线程池（core 4 / max 8），PDFBox 解析会把整份 PDF 读进内存，并发几个解析任务就能把剩余的那两三百兆冲爆，触发 OOM Killer——被杀的往往是 MySQL 或 Java 进程，表现为"服务莫名其妙挂了、重启才好"。

4 GiB 稳态占用 45% 左右，剩余 2 GB 足够扛住解析峰值和 GC 抖动。**这 21 天的额度差（见下节）不值得拿稳定性换。**

## 三、算力包额度怎么用最划算

截图信息：额度 **850 元**，每小时剩余额度 1.14 元，到期 **2027-04-18**。从今天到到期只有 **174 天**。

| 规格 | 单价(元/时) | 日成本 | 额度可撑 | 实际能用 | 用尽日期 |
|---|---|---|---|---|---|
| 2C 2G 经济型 e | 0.11376 | 2.73 元 | 311 天 | **174 天（包到期）** | 2027-04-18 |
| **2C 4G 经济型 e** | **0.23166** | **5.56 元** | **153 天** | **153 天** | **约 2027-03-28** |
| 2C 8G 经济型 e | 0.33296 | 7.99 元 | 106 天 | 106 天 | 约 2027-02-09 |
| 4C 8G 经济型 e | 0.43416 | 10.42 元 | 82 天 | 82 天 | 约 2027-01-16 |
| 2C 2G 通用算力型 u1 | 0.25791 | 6.19 元 | 137 天 | 137 天 | 约 2027-03-11 |

**这里有个反直觉的点**：2C2G 看起来"能用更久"，但它在 2027-04-18 到期时只花掉 2.73 × 174 ≈ **475 元**，剩下约 **375 元额度直接作废**。2C4G 则是 850 元刚好用满 153 天，一天不浪费。

也就是说，**选 2C4G 不会多花钱，只是把"会作废的余额"换成了内存**；代价是最后提前约 21 天停机（3 月底 vs 4 月中）。对求职演示场景，3 月底已覆盖主要面试窗口。

> 若 4 月还有面试，剩 21 天的成本约 117 元，可以按量付费续，比一开始就选小规格导致 OOM 更划算。

**另外要核对账单**：算力包通常只抵扣 vCPU + 内存。40 GiB ESSD Entry 系统盘、超出 20 GB/月 的公网流量是单独计费的，出第一个月账单时确认一下，别以为 850 元是"全包"。

## 四、部署形态

```
                    ┌─────────────────────────────────────┐
   浏览器            │  ECS 2C4G  Alibaba Cloud Linux 3     │
      │             │                                      │
      │  http://IP:8090                                   │
      ▼             │  ┌──────────────────────────────┐   │
 ┌─────────┐        │  │ Nginx                        │   │
 │ 用户端   │───────▶│  │  /        → /var/www/rag-qa  │   │
 └─────────┘        │  │  /api/    → 127.0.0.1:8080   │   │
                    │  └───────────┬──────────────────┘   │
                    │              ▼                       │
                    │  ┌──────────────────────────────┐   │
                    │  │ Spring Boot 8080  (仅回环)    │   │
                    │  └───────────┬──────────────────┘   │
                    │              ▼                       │
                    │  ┌──────────────────────────────┐   │
                    │  │ MySQL 8.0  3306   (仅回环)    │   │
                    │  └──────────────────────────────┘   │
                    │  /data/knowingorder  原件与临时目录   │
                    └─────────────────────────────────────┘
                                   │ 出网（HTTPS）
                                   ▼
                    Tavily 搜索 · DashScope 模型 API
```

**为什么走同域反代**：前端所有请求都是相对路径 `/api/...`（`enterprise.ts`、`api.ts` 中可见），由 Nginx 统一转发，浏览器看到的只有 `http://IP:8090` 一个源。这样：

- 不需要配 `CORS_ALLOWED_ORIGINS`（生产默认留空 = 不开放任何跨域，正好安全）
- `SameSite=Lax` 的会话 Cookie 不会因跨站被拦
- 前端不需要任何构建期环境变量，`vite build` 产物直接丢给 Nginx 即可

## 五、访问方式：无域名，长期走 IP + 端口

已确定**暂不购买域名**，因此没有备案，也没有 HTTPS。访问入口固定为：

```
http://<公网IP>:8090
```

ECS 公网 IP 在实例存续期间不变，可以放心当作固定地址（只有释放实例或更换弹性公网 IP 才会变）。

### 三条由此产生的硬约束

**① 80 / 443 用不了。** 境内 ECS 未备案时这两个端口的访问会被管控，直接打 `http://IP` 打不开或跳拦截页。必须用高位端口，Nginx 监听 8090，安全组只放行 8090。

**② 会话 Cookie 的 Secure 必须关掉。** 这就是 P0-1。开着 `secure: true` 时浏览器不会在 HTTP 下回传 `JSESSIONID`，登录接口返回成功、下一秒请求又变未登录，现象极具迷惑性。

**③ 口令和会话以明文经过公网。** HTTP 没有加密层，同一网络里的任何人都能抓到登录 POST 的密码和 Cookie。

### 所以数据边界必须守住

| 允许 | 禁止 |
|---|---|
| 演示用的虚构学校/企业数据 | 任何真实公司文档、真实员工信息 |
| 专门的演示账号 | 你常用的、和其他平台复用的密码 |
| 面试时的即时问答 | 把地址发给一群人长期使用 |

具体做法：
- 演示账号用独立密码，**不要复用任何真实平台的口令**
- 演示账号只授予演示所需的最小权限，别用超级管理员日常登录
- 上传的文档全部是虚构/公开资料；`docs/` 里的真实业务说明不要上传到演示空间

### 什么时候会不得不买域名

出现下面任一条，就该去备案了：

- 要放**任何真实数据**（HTTP 明文传输不可接受）
- 要把地址写进简历/发给面试官，`http://47.x.x.x:8090` 观感确实差
- 需要 80/443 标准端口
- 需要多个服务共用一个入口

备案要 7–20 个工作日，**真要用的时候再办是来不及的**。建议在拿到 offer 前一个月评估一次。

### 想要 HTTPS 但不想备案的过渡办法

用内网穿透拿一个临时 HTTPS 子域名（ngrok 免费版给 `xxx.ngrok-free.app` 这类地址）。优点是浏览器地址栏是 https、证书可信；缺点是境内访问不稳定、有流量限制、且流量要绕境外一圈。**只适合短时演示，不适合日常挂着。**

要提醒的是：这类方案不改变"数据不能是真实的"这个前提——只是把明文传输这一条补上了，机器还是那台演示机。

## 六、上线前必须先处理的三件事

### P0-1 会话 Cookie 的 Secure 标志 ✅ 已处理

| | |
|---|---|
| 原状 | `application-prod.yml` 中 `cookie.secure: true` 硬编码 |
| 后果 | 纯 HTTP 访问时登录态无法保持，前后端都正常但就是登不进去 |
| 改动 | 已改为 `secure: ${SESSION_COOKIE_SECURE:true}`，**默认仍为 true**，只在部署环境显式覆盖 |
| 用法 | 无域名演示：`env` 里写 `SESSION_COOKIE_SECURE=false`；将来接入 HTTPS：删掉该行即回到 `true` |
| 风险 | 设为 false 期间 Cookie 明文公网传输，仅限虚构/演示数据；**任何真实资料上线前必须切回 HTTPS** |

### P0-2 Windows 路径硬编码（会导致文件存在奇怪位置或写入失败）

`application.yml` 里两处默认值是 Windows 路径：

```yaml
multipart.location: ${KNOWLEDGE_UPLOAD_TEMP:E:/Codex/home/tmp}     # 第 33 行
storage-root:        ${KNOWLEDGE_STORAGE_ROOT:E:/Codex/data/...}   # 第 103 行
```

Linux 上不设环境变量时，会在工作目录下真的建一个名为 `E:/Codex/...` 的目录（能跑，但极难排查）。部署时必须显式指定：

```bash
KNOWLEDGE_STORAGE_ROOT=/data/knowingorder/knowledge
KNOWLEDGE_UPLOAD_TEMP=/data/knowingorder/tmp
```

这两个目录要 `chown` 给运行账号，且**不能被 Nginx 映射为静态资源**。

### P0-3 首次管理员不能靠启动应用创建

`BootstrapAdminCommand` 是独立主类，靠三个环境变量一次性执行：

```bash
KNOWINGORDER_BOOTSTRAP_ENTERPRISE / _USERNAME / _PASSWORD
```

执行完必须把这些变量从环境中移除，**不能写进 systemd 的 Environment 里**。另外建库顺序是：**新库只执行 `schema.sql`**（已含 20261017~20261020 的 10 支增量内容），再补两支 schema 未收录的增量（`20261025_01_affairs_subsidy.sql` 建 8 张事务表并把 `chk_member_role` 加上 `FINANCE`；`20261025_02_knowledge_chat_soft_delete.sql` 加 `deleted_ms`）。**已有库不能重放 schema.sql，也不能对空库重放 20261017~20261020 那 10 支——会因重复建表中断（ERROR 1050）。**

### 顺带要留意的 P1

- **登录限流按直连地址计数**：`LOGIN_PER_ADDRESS_PER_MINUTE` 默认 10。经 Nginx 反代后所有请求源都是 `127.0.0.1`，等于全站共用"每分钟 10 次"的额度。单人演示无影响，若多人同时登录需调高。
- **两个开发期入口已按不同方式处理**（2026-10-26 改动）：
  - **商品查询 `/api/products/search`**：去掉 `@Profile("dev")`，生产环境直接可用。返回的是代码里固定的示例目录（`MockProductSearchService`），不查真实门店、不产生订单，`simulated: true` 会在响应里标注；接入真实渠道时用 `knowingorder.products.provider` 切换实现。员工事务页的布局因此保持原样。
  - **联网问答体验 `/api/chat`**：仍是开发期功能，接口保持 `@Profile("dev")`，生产环境 404。前端在 `publicChatEnabled` 为 false 时把页面切成"未开启"说明态，并给出两条真实可走的路径（去企业问答 / 打开公开搜索引擎），不再出现点进去报错的情况。侧栏入口保留，界面不会因此变空。
  - **需要临时演示联网问答时**：前端构建加 `VITE_PUBLIC_CHAT=true`，后端去掉 `WebChatController` 的 `@Profile("dev")`，并给 Nginx 的 `/api/chat` 加 `limit_req`（该接口无需登录，会消耗外部搜索与模型额度）。
- **`/api/auth/revoke-sessions`、`EnterpriseResourceController` 6 个接口**目前无前端入口，属于预留。

## 七、部署步骤

### 1. 本地打包（Windows 侧）

```bash
cd backend && ./mvnw clean package -DskipTests
cd frontend && npx vite build
```

产物：`backend/target/rag-qa-0.0.1-SNAPSHOT.jar`（约 38 MB）、`frontend/dist/`（约 500 KB）。
**注意**：`target/` 里的旧 jar 可能不是最新代码，务必重新打包。

### 2. 服务器初始化

已封装成脚本 `backend/deploy/bootstrap.sh`，做四件事：装 JDK/Nginx/MySQL、建运行账号与目录、调低 MySQL 内存参数、配 2 GiB swap。幂等，可重复执行。

```bash
# 本地打包后一并上传
scp -r backend/deploy root@<公网IP>:/tmp/deploy
scp backend/target/rag-qa-0.0.1-SNAPSHOT.jar root@<公网IP>:/tmp/app.jar
scp -r frontend/dist root@<公网IP>:/tmp/dist

# 服务器上执行
sudo bash /tmp/deploy/bootstrap.sh
```

脚本会自检 MySQL 版本（低于 8.0.16 直接中止）、检测已有 swap 不重复建、firewalld 在用时自动放行 8090。跑完打印剩余的人工步骤。

> 手动等效命令（不用脚本时）：
> ```bash
> dnf install -y java-17-openjdk-headless nginx mysql-server tar
> mysql --version          # 必须 ≥ 8.0.16
> systemctl enable --now mysqld nginx
> useradd -r -s /sbin/nologin ragqa
> mkdir -p /opt/rag-qa /var/www/rag-qa /data/knowingorder/{knowledge,tmp}
> chown -R ragqa:ragqa /opt/rag-qa /data/knowingorder
> ```

### 3. 数据库

```bash
mysql -uroot -p
```

```sql
CREATE DATABASE rag_qa DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'rag_qa_app'@'127.0.0.1' IDENTIFIED BY '<强密码>';
GRANT SELECT,INSERT,UPDATE,DELETE,CREATE,ALTER,INDEX,REFERENCES ON rag_qa.* TO 'rag_qa_app'@'127.0.0.1';
FLUSH PRIVILEGES;
```

导入（新库）：

```bash
# 1) 基础结构：schema.sql 已包含访客、权限、知识空间、向量发布等全部基础表（23 张）
mysql -uroot -p rag_qa < backend/schema.sql

# 2) 只补 schema.sql 未收录的两支增量
mysql -uroot -p rag_qa < backend/sql/migrations/20261025_01_affairs_subsidy.sql
mysql -uroot -p rag_qa < backend/sql/migrations/20261025_02_knowledge_chat_soft_delete.sql

# 3) 演示数据（可选）
mysql -uroot -p rag_qa < backend/sql/demo/20261025_seed_demo_data.sql
```

> 20261017~20261020 那 10 支增量是给**已有旧库**升级用的，内容已并入 `schema.sql`。对空库执行会在第一条 `CREATE TABLE rag_guest_identity` 处报 `ERROR 1050 Table already exists` 并中断，属预期行为，不是数据损坏。若已误跑，删库重来即可（空库无损失）。
>
> `backend/sql/demo/20261024_replace_school_data.sql` 是「先 DELETE 再重建」的替换脚本，只供 PowerShell 脚本以批处理方式调用，**新库绝对不能执行**。

调低 MySQL 内存（4 GB 机器）：

```ini
# /etc/my.cnf.d/ragqa.cnf
[mysqld]
innodb_buffer_pool_size = 256M
max_connections = 60
```

### 5. systemd 托管

仓库里已备好三份模板，直接套用即可，不用手抄：

```bash
# 应用与目录
install -m 644 backend/deploy/rag-qa.service /etc/systemd/system/rag-qa.service

# 环境变量（含密码，权限收紧）
install -d -m 750 /etc/rag-qa
cp backend/deploy/env.prod.example /etc/rag-qa/env
chmod 600 /etc/rag-qa/env && chown root:ragqa /etc/rag-qa/env
vi /etc/rag-qa/env            # 填 DB_PASSWORD、API Key；确认 SESSION_COOKIE_SECURE=false

systemctl daemon-reload
systemctl enable --now rag-qa
systemctl status rag-qa --no-pager
journalctl -u rag-qa -f       # 首次启动盯这里
```

模板里的关键取舍：
- `-Xmx512m` + `MaxMetaspaceSize=192m` + `UseSerialGC`：4 GB 机器上比 G1 省内存，堆固定避免伸缩抖动
- `HeapDumpOnOutOfMemoryError`：真 OOM 时留现场，便于判断是谁吃掉的
- `ProtectSystem=full` + `ProtectHome=true` + `ReadWritePaths`：把可写范围收紧到 `/data/knowingorder` 和 `/opt/rag-qa`
- 密码写在 `EnvironmentFile` 里而不是 `Environment=`，避免 `systemctl cat` 或 `ps` 直接暴露

### 6. Nginx

```bash
install -m 644 backend/deploy/nginx-rag-qa.conf /etc/nginx/conf.d/rag-qa.conf
nginx -t && systemctl reload nginx
```

模板要点：
- `listen 8090`（未备案不能用 80）
- `try_files $uri $uri/ /index.html`：SPA 深链接刷新不 404
- `/api/` 反代到 `127.0.0.1:8080`，`proxy_read_timeout 120s`（问答 30s、chat 105s，留余量）
- `proxy_request_buffering off`：上传不落 Nginx 临时盘
- `index.html` 不缓存、`/assets/` 长缓存：发版后不会出现"旧 HTML 指向已删除的 JS"
- `server_tokens off`：不暴露 Nginx 版本
