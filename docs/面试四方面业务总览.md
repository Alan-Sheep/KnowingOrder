## 1. 产品一句话

**知序（KnowingOrder）是企业知识与工作助手**，界面标语「读懂公司知识，帮你把工作做好」。

它要解决的不是「聊天」，而是三件具体的事：

1. 员工能查到**自己有权限看、当前还在生效、能核对出处**的公司制度与流程；
2. 查完之后能接着**办具体的事**（报销、订餐、结算）；
3. 资料不够、过期、有冲突时**明确说出来**，而不是编一个看起来像答案的结论。

三条业务线的主次关系是定死的：

| 业务线 | 定位 | 说明 |
|---|---|---|
| 企业知识库与业务问答 | **主线** | 优先投入开发、评测和上线验收 |
| 员工事务与补贴结算 | 辅助 | 首个场景是加班餐／部门订餐 |
| 通用聊天、公开搜索、外卖平台跳转 | 支持能力 | 不能替代企业知识库的产品价值 |

**首个落地场景是学校**：把学校当作一个组织，师生当作组织成员，复用现有企业／部门／成员／知识空间模型。不改数据库名和 Java 包名，不新增教务系统，演示企业是虚构的「知序大学」。

## 3. 主线：企业知识问答

### 3.1 员工视角的完整路径

```
登录（管理员开户，账号密码）
  → 自动识别所属企业（单企业自动连接，多企业按名称选）
  → 选择已授权的知识空间
  → 提问（上限 1200 个字符，可一句话多问）
  → 受理成持久任务（记下编号，刷新后能查回原任务）
  → 判断问题属于什么业务（学校范围识别）
  → 在授权范围内检索（关键词，可选混合）
  → 判断资料够不够
  → 生成结论（仅限获准的合成空间）
  → 引用字面校验 + 结论支持复核（后者 2026-10-24 才加）
  → 引用再次核对权限
  → 给出四种结论之一 + 出处
  → 追问 / 反馈 / 换会话
```

> 注意中间两行的区别：**字面校验**是早期就有的（引文必须是所选片段的连续原文、来源号有效、问题被完整覆盖），**结论支持复核**是 2026-10-24 补的（同模型再跑一次，判断引文是否真能支持这句话）。原文自己写明「原文存在不证明结论语义成立」，所以这两件事不能合并成一句「检查引用是否正确」。

### 3.2 每一环的业务说明

| 环节 | 业务规则 | 不给用户添的麻烦 |
|---|---|---|
| 登录 | 管理员开户 + 账号密码，**不开放公众注册**；闲置 30 分钟、绝对 8 小时，读取不延长绝对期限 | 不需要理解数据库企业编号 |
| 归属企业 | 从可信登录身份查有效成员关系；单企业自动连，多企业按名称选，零企业提示找管理员 | 员工不用手填编号 |
| 选空间 | 只列出已授权的空间 | 不需要记空间编号 |
| 提问 | 上限 1200 个字符（UTF-16 代码单元，**不是 token 也不是汉字个数**）；一句话多问拆成最多 3 个分项 | 按原文顺序呈现，不要求员工排优先级 |
| 受理 | 每条请求有唯一编号，重复提交不会产生两笔任务；同一文档版本同时只允许 1 个在途任务 | 刷新后能按原编号查回任务 |
| 范围判断 | 先判定「属不属于这个组织的业务」 | 不属于就直说，不硬凑条款 |
| 检索 | 只检索**已发布 + 解析就绪 + 在有效期 + 有权限**的片段；维护者自己也不能用草稿作答 | 检索不到不等于资料不存在（不泄露无权资料） |
| 资料充分性 | 「检索到候选」和「能回答」是两件事，分开判断 | 资料不够就说不够，不猜金额、不猜到账日期 |
| 生成 | 默认只展示原文；只有服务端配置的「企业:空间对」白名单才允许调模型 | 客户端无法自行打开外发许可 |
| 结论复核 | ①字面校验：引文必须是所选片段的连续原文、来源号有效、问题被完整覆盖；②支持复核（10-24 加）：逐段判断引文能不能支持这句话，一段不通过就隐藏该分项。**但复核和生成用的是同一个模型，可能一起错** | 宁可不答，不给出没有依据的结论 |
| 引用核权 | 送模型前、返回前都重查权限；点开引用时再查一次当前权限和有效版本 | 资料撤回或撤权后，旧的引用打不开 |
| 追问 | 历史只作话题线索，不作制度依据；默认关闭 | 关联不确定时明说，不硬套上一轮话题 |
| 反馈 | 只有本人已完成的任务能提交；员工提交 → 有维护权限的人处理，靠版本号防两个处理者互相覆盖 | 反馈不会直接改写已发布制度 |

> **「引用核权」那格要说得更准一点**：页面上已经显示的文字，技术上收不回来；已经发到模型的内容也撤不回。系统能保证的是「下次打开时拒绝」，不是「从记忆里抹掉」。原文明确写了这条边界，面试时照实说反而更站得住。

### 3.3 回答的四种业务结论

这是这套系统最核心的业务设计——**除了"答"和"不答"，还区分"只答一部分"和"资料打架"**。

| 结论 | 什么时候出现 | 用户看到什么 |
|---|---|---|
| 有据可答 | 资料充分且相关 | 结论 + 每条结论对应的原文位置 |
| 部分可答 | 一部分有依据，一部分缺 | 先答有依据的部分，明确指出缺什么依据 |
| 无依据 | 检索到了候选但撑不住结论，**或者干脆没检索到东西** | 「当前获授权资料不足以确认，请联系负责人」 |
| 资料冲突 | 两份资料说法不一致／版本重叠 | 展示冲突范围，说明不能直接确定，不按更新时间随意覆盖 |
| 范围外 | 不属于本组织业务 | 「不属于当前知识库服务范围，可主动切换到通用问答」，不自动跳转 |

**混合问题的处理**：一句话里既有校内又有校外，保留原问题和原序，校内部分照常处理，校外部分单独提示——不是整句拒绝，也不问用户"先处理哪个"。

除了这四种结论，还有四个用户会真实遇到的状态，讲的时候别漏：

| 状态 | 含义 |
|---|---|
| 仅证据（本地零外发） | 默认模式下只给授权原文片段，不生成结论——这是「保守」而不是「失败」 |
| 模型不可用 | 模型或格式出错时明确说不可用，保留已获准的原文，**不偷偷换成公开搜索** |
| 范围未确认 | 判断不出来时既不说「没这条规定」，也不伪装成「无依据」——只提示范围尚未确认 |
| 范围服务不可用 | 未获准外发的空间、分类超时、标签非法等情况一律明确提示，**零自动重试** |

这四个状态的意义在于：**"不确定"本身要如实呈现，不能被压成"没有"**。把 UNKNOWN 说成 NO_EVIDENCE，是目前最容易被抓住的一种失真。

### 3.4 范围判断为什么不能靠关键词

「宠物保险」不能设成全局禁词：原文的例子是本校确实开设宠物保险课程，所以这个词仍属校内业务，设成禁词会把真问题拒掉。判断依据是**服务端配置的组织业务范围 + 当前原问题（以及可信追问带过来的上一问）**——识别时只发范围编号和问题，不发身份编号和文档内容。分类标签只是路由，**不能当授权凭据**。

四件事是分开的，不能互相替代：

- **范围**回答「这问题属于什么业务」
- **向量相似度**回答「文字**语义**接近程度」（不是字面像不像）
- **授权**回答「这个人能不能读」
- **证据充分性**回答「这些资料能不能支持结论」

识别和生成共用一份预算：先识别一次，再把校内问题**批量生成一次**（最多 3 个分项、共享 6 段授权证据），不按子问题各调一次模型。代价是多个问题共用召回窗口，**不保证每项都有候选**——这是刻意的取舍，别当成 bug。

### 3.5 这条线明确「不做」的事

- 不用模型常识或公开网页替代企业制度
- 不把「有权限读」当成「可以回答」
- 不在资料不足时给一个像模像样的结论
- 不把企业内部正文发给未获授权的模型（默认零外发）
- 不因没搜到就自动转公开搜索（要用户自己点，且不携带问题和原文）
- 不让模型决定补贴金额或把问答自动变成办理

**关于「零外发」要补一句**：外发许可是环境变量里的「企业:空间对」白名单，空值即本地模式；而且**已经发出去的数据撤不回来**——复核只能保证「下次不放行」，不能保证「从外部抹掉」。原文还特别提醒：白名单是空间级的，**不是内容分类器**，所以严禁把真实资料放进获准的空间来「顺便测试」。这条比单说「默认零外发」更经得起追问。

## 4. 主线：组织与权限治理

### 4.1 三个概念要分清

| 概念 | 含义 | 常见误解 |
|---|---|---|
| 账号 | 登录身份 | 账号存在 ≠ 是这个企业的成员 |
| 企业成员 | 这个账号在某企业的角色、部门、状态 | 成员 ≠ 什么都能看 |
| 空间授权 | 明确授予某成员对某空间的操作权 | 管理员 ≠ 能读私有知识或他人会话 |

登录层统一是普通用户身份，**企业管理员不是系统级管理员**——一个企业的管理员不会自动成为全局管理员，也不会因为管组织就能读别人的会话。

### 4.2 权限的业务规则

- 角色上**已实现**的是三类：员工、企业管理员、知识维护者。需求文档里还设计了「财务」这一角色，但代码里没有独立财务角色，别把它说成已实现。
- 权限在**读数据的那一刻**绑定，不是进页面时查一次就完事；首版每次都查数据库，不提前上缓存。
- 撤权、调岗、停用后，之前的会话、快照任务同时失效；打开旧答案时逐条复核，权限没了就整份隐藏。
- 部门是**平级**的（没有树），每个成员最多一个直属部门。停用一个部门前必须把成员全部移出并撤销该部门的授权——系统**不会自动帮管理员搬人或撤权**，不满足条件就拒绝停用。
- 成员变化递增该成员的权限版本；部门变化会保守地递增企业级版本，可能顺带结束一些无关的旧任务——这是刻意选的安全侧。
- **停用成员不等于删账号，也不抹掉已有的空间授权**。重新启用时，原来的明确授权可能跟着回来，所以页面必须让管理员确认这一点。这是最容易变成越权的一格。
- 防刷：每个直连地址每分钟 10 次、全局每分钟 120 次。都是单节点保护，不要说成分布式限流。

### 4.3 为什么不做「默认企业 1」

换库、加企业、迁移账号时，默认值会把人放进错误的上下文。宁可让员工多点一次，也不猜。

## 5. 主线：资料治理

### 5.1 资料的生命周期

```
上传原件（单件 ≤1MiB，整个表单 ≤2MiB）
  → 受理成入库任务（可查询、可取消、可重试）
  → 解析成文字并切分片段（带行号／页标记，可定位）
  → 形成草稿版本
  → 发布（此时才进入「可被检索」的范围）
  → 撤回 / 删版本 / 删文档
```

四个动作是分开的：**发布、撤回、删版本、删文档**。三条容易答错的细则：

- **撤回不回退旧版**。撤回就是「当前没有生效版本」，不会自动把上一版顶上来。
- **已发布的版本要先撤回，才能删版本**；删整篇文档会清掉发布指针。
- 发布前要核对实际片段数和生效期，切换是原子的（不会出现新旧版本同时生效的中间态）。

关键业务约束：

| 约束 | 原因 |
|---|---|
| 草稿、解析失败、未发布的版本**不进问答**；维护者自己也不能拿草稿作答 | 否则员工会读到半成品 |
| 发布 = 授权成员可以读，**不等于**已经能向量检索或生成回答 | 两个概念常被混为一谈 |
| 反过来也成立：**索引能建 ≠ 能用于问答**。草稿或已撤回版本可以建索引，但不能当回答依据；索引核对通过（VERIFIED）也还不等于可用（READY） | 建索引和允许引用是两道门 |
| 格式：UTF-8 TXT／Markdown 起步，后加文字层 PDF 和普通 DOCX | 完全不解析图片、也不做模型读图；旧 DOC 不支持 |
| 单件 1MiB、整个上传表单 2MiB；不知道内容长度的请求直接不受理 | 明确边界，不假装能传大文件 |
| 解析的硬边界：PDF 最多 100 页，加密的、扫不出文字层的、伪装扩展名的都拒绝；DOCX 只提取正文段落和表格文字，拒绝宏和外部引用；文字上限 50 万字符、最多 1000 段 | 这些数字是拒绝垃圾输入的门槛，不是性能指标 |
| 撤回后旧引用打不开 | 不能让旧链接绕过撤回 |
| 已发布的版本拒绝「重建」 | 防止把线上资料悄悄换掉，要改就传新草稿版本 |

### 5.2 入库任务的业务规则

- 全库最多 64 条在途，每成员 2 条，**同一文档版本同时只允许 1 条**，单节点 2 个执行槽，从受理起 30 秒总截止（排队和恢复都扣同一份余额，不延长、不无限重试）。
- 取消之后解析迟到的结果会被丢弃，不会把已取消的任务写成完成。
- 重启后靠租约恢复，但**只恢复一次**，第二次直接判「恢复次数用尽」转人工。原文还明确写了「没有真的杀进程做过实库演练」，所以别说成「所有崩溃点都验过」。
- 员工看到的永远是「未执行 / 处理中 / 成功 / 失败 / 已取消」，不是一句「出错了」。
- **点了上传却没收到回执**是员工最容易慌的一格：页面只在内存里留着文件和编号，刷新或关页就丢了。这时口径是「先核对数据库里的目录，确认有没有生成」，而不是让员工重新传一遍——重传会多一条任务。

> **一个刻意的对比**：入库任务挂了可以恢复，问答任务挂了**不自动重放**。原因是解析是幂等的，重跑一遍结果一样；而调模型不保证「恰好执行一次」，猜上游可能已经出了结果，会出现重复计费或两份不一样的答案。所以问答任务重启后只等原截止时间走完，然后如实告诉用户「这次没成功，可以重发」。

### 5.3 索引与检索策略

- 向量索引是**高级维护**，平时不用管；页面上写清楚「当前用哪种检索方式」，因为这是后端配置，不是用户选项。
- 混合检索（关键词 + 向量）已接线但**开关默认关闭**；关闭时走原来的关键词路线。
- 页面显示的策略，不代表历史任务用过这个策略，也不代表依赖健康或索引就绪。
- **索引可用性的判定标准**：不能因为「集合存在」「第一批跑完」「总点数够了」就宣布可用。要逐条核对预期清单，任何缺失或摘要不符就整批拒绝；最后一批返回空就报冲突、禁止发布。
- 索引的完整链路已经跑通：不可变清单 → 模型快照核验 → 授权受理 → worker → **显式发布成 READY** → 新代次 CAS 切换 → 撤回。三种状态都有真实验收（发布 revision=1、切换 revision=2、撤回 revision=3），而且**撤回不退回旧代次**，用旧任务或旧修订去发布会报业务冲突。
- **构建完成不等于自动上线**：worker 跑完是「已核验」，发布指针仍是未发布，要人显式点发布。这条是刻意设计——索引错了不该自动生效。
- 还没完成的是：开发 MySQL 的原生事务/并发验收、主应用里混合检索开关仍是关的、前端检索策略文案写死没消费接口。所以「向量链路验收通过」和「问答已经用上向量」还是两句话。

## 6. 辅助：员工事务与补贴

> **口径提醒**：`02-需求分析` 在 2026-10-24 明确「辅助补贴本轮暂缓，只做知识库主线」。后端确实已有规则、资格、申请、凭证、审批、结算、退款的接口代码，但 `docs/` 里没有这一块的实施与验收记录。所以本节只写**已确认的业务规则**，不写实现状态。

### 6.1 下单边界

系统只做「查询推荐 + 跳转」，**员工在外部平台自己下单和支付**。

- 系统内不创建平台订单、不代付款、不模拟支付回调。
- 点击、跳转、员工口头告知都**不构成可信订单事实**。
- 开发阶段用 Mock 商品，明确标注是测试数据，不进入财务事实；生产禁止静默回退 Mock。

### 6.2 补贴闭环的七步

1. 员工提交申请，关联外部订单信息、消费时间、参与人、分摊和原始凭证。
2. 系统按**明确、带版本的企业规则**检查资格、金额和额度（不交给大模型裁定）。
3. 被选中的其他员工收到本人参与通知，核对金额和分摊后**明确确认**；不回复不算同意。
4. 名单、金额或分摊变了，生成新版本，受影响的人**重新确认**——旧确认不能批准新内容。
5. 核验履约、确认和材料后，才能提交财务核算；数据不明转人工，不直接标「已完成」。
6. 财务查看获授权申请、证据和核算结果，形成月度清单。
7. 保留审核、结算和调整记录。**系统结算状态 ≠ 工资已发**。

### 6.3 退款与异常

| 情况 | 业务处理 |
|---|---|
| 已取消或全额退款 | 不作为有效补贴依据 |
| 部分退款 | 按实际净支出重新核算 |
| 已提交未结算时发现退款 | 阻止按旧金额结算，保留撤回过程并通知相关人 |
| 已结算后发现退款 | 新增调整记录，保留原结算事实，不覆盖历史 |
| 数据延迟／报表缺失／超时 | 先标「待核验」，限定时间和次数重查原记录，必要时转人工 |

### 6.4 三类追溯依据（无 OCR）

| 依据 | 说明 |
|---|---|
| 结构化业务记录 | 渠道授权数据，或员工填报且已核对；**用户填报不能标成平台认证** |
| 原始凭证 | 保存原始票据图片／电子发票原件，不只存截图 |
| 过程记录 | 参与确认、人工核对、规则版本、额度变化、结算、退款调整，含操作者与时间 |

## 7. 质量怎么证明

这部分是 `docs/` 里最特别的地方：**每条结论都要说清楚「证明了什么、没证明什么」**。

| 验证 | 做法 | 结果 | 不能说明什么 |
|---|---|---|---|
| 企业黄金集对照 | 20 份虚构资料、24 道题，关键词 vs 混合检索，同一环境 | 标注依据召回 14/15 → 15/15；找齐全部依据的正例 11/12 → 12/12；MRR 0.9167 → 1.0000；越权等错误 0 | 不是「24 条答案全对」，没调回答模型 |
| 证据边界契约测试 | 20 项，覆盖四种结论和引用解析 | 19 项验证契约，**1 项故意记录「错误结论被放行」的已知漏洞** | 不是安全防护通过；10-24 加的复核是**模型侧缓解层**，不等于契约漏洞修好，缓解层本身也没用真实模型验过 |
| 向量链路联合验收 | 真实本机 Ollama + Qdrant（bge-m3，1024 维）+ 生产服务调用链 | 后端向量 928/928、前端 43/43、企业/向量页面 38/38 | 928 是 19 组**子集**，与 2630 全量有重叠，不能相加；也不是「MySQL + 浏览器 + 回答模型」三者联合验收 |
| 真实权限切换 | 同一成员依次 NONE → READ → MAINTAIN → REVOKED | 13/13：无权不读、只读不能上传、维护可发布、撤权后旧会话也读不到 | 不是两个真实企业账号互访，也不是并发撤权 |

**黄金集那行有一半是坏消息，讲的时候别只报好的**：

| 指标 | 关键词 | 混合 | 说明 |
|---|---|---|---|
| 召回（12 道正例、15 个目标片段） | 14/15 | 15/15 | 混合确实更好 |
| 找齐全部依据 | 11/12 | 12/12 | 同上 |
| **无依据却仍给出候选（8 道）** | 7/8 | **8/8** | **混合变差了**：本来该说「没依据」的题，全部都有候选了 |
| 检索累计耗时 | 3783 ms | 27533 ms | 约 7.3 倍，原文注明不是公平压测，但代价是真的 |

所以正确结论是「**召回更全，但同时引入更多噪声，可回答性没有被证明**」，不是「混合全面更好」。原文还专门写了「这不是 8 道错误答案，也不能称为拒答通过」。

> **另一个容易说错的点**：2026-10-19 还有一轮 H2 关键词基线，数字是 12/15→14/15、9/12→11/12，分母也是 15 和 12。两轮实验**共用分母但不是同一件事**，引用时必须说明是哪一轮。

## 8. 状态口径：三种「完成」必须分清

这是这套文档最值钱的纪律。汇报时如果混用，一句话就会被追问穿。

| 说法 | 含义 | 例子 |
|---|---|---|
| **已完成** | 代码 + 测试 + 真实库／真实页面都有证据 | 组织与成员管理、入库任务、权限切换 |
| **代码已接线，默认关闭** | 能跑，但配置开关是 false，未经真实质量验收 | 多轮追问、查询扩展、混合检索 |
| **只有设计** | 文档写清了规则，代码还没写 | 补贴协同、部门树、多角色、SSO、OCR、访客额度 |

还有一条容易踩的：**测试数量不等于正确率**。2630 项是当前最新的后端全量（88 份测试报告），但它跑在隔离库和替身上，**不含真实 MySQL、真实 Qdrant、真实模型的集成测试**，也不说明答案对、更不说明能上线。同一条时间线上还有 762 / 1458 / 1592 / 1622 / 1642 / 1738 / 2347 / 2589 这些数字，都是不同时点的全量，**不能相加也不能并列引用**；928 是向量相关的 19 组子集，和 2630 有重叠，同样不能加。

## 10. 面试官最爱追问的八个问题

深挖笔记第 17 节列了八条「必须能追问到底」的问题。下面是每个问题的答案要点，以及本文哪里能查到：

| # | 问题 | 怎么答 | 本文位置 |
|---|---|---|---|
| 1 | 文档怎么切，1000 和 120 怎么定？ | 块长 1000、重叠 120，是**按字符数设的初始保护参数，不是 token 数**，也不是调优结果 | 5.1 |
| 2 | 用什么 Embedding 和向量库？ | bge-m3（1024 维）＋ Qdrant；**向量只用于找候选，正文仍从 MySQL 取**，不是把正文存进向量库 | 5.3、7 |
| 3 | top-k、阈值、召回不准怎么调？ | 中文双字词切分、最多 48 个词、固定 SQL 定位、最多 24 个候选、去重重叠后最多 6 段；**没有设余弦阈值** | 5.3 |
| 4 | 来源怎么保证，能彻底防幻觉吗？ | 不能。能保证的是「引文是连续原文、来源号有效、问题被完整覆盖」，再加一层同模型复核；同模型可能一起错 | 3.2、3.3、9 |
| 5 | A 公司拿到 B 公司的空间编号怎么办？ | 编号不赋权，权限在每次读数据时按当前成员关系绑定；越权和不存在统一返回同样的错误，避免探测 | 4.1、4.2、7 |
| 6 | 多问、多轮、流式怎么管？ | 一次最多 3 个分项、共享预算；追问默认关闭；**流式（SSE）没做**——原因很实在：内容先流出去，最后拒绝就收不回来了 | 3.2、3.4 |
| 7 | 并发和超时怎么办，重试会不会卡死？ | 单节点 2 个槽、**不排队**、满载直接拒绝、到点取消等待、**不自动重试**；问答挂了不重放 | 5.2 |
| 8 | 大文件慢、上下文长怎么优化？ | 单件 1MiB／表单 2MiB、文字上限 50 万字符、最多 1000 段；生成只取 6 段；30 秒总截止不续期 | 5.1、5.2 |

其中第 6 条和第 2 条最容易答错，原因写在下面：

- **流式的取舍**：流式体验好，但一旦先吐字，最后发现依据不足也没法收回——这和「宁可只答一部分」的设计是冲突的。所以现在的选择是「先算完再显示」，代价是等待感。
- **向量只做候选**：向量库里存的是向量和定位信息，正文仍以数据库为准。这样资料撤回、权限变化、版本切换都能立刻生效，不会出现「向量库里还留着旧正文」的问题。
