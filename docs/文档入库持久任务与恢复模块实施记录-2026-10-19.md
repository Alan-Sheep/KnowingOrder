## 1. 本轮解决什么问题

原流程是浏览器同步请求`parse`，文件解析与片段提交已有事务保护，但没有持久受理记录，刷新后难以区分“未执行”和“已执行但没收到回执”。本轮新增数据库入库任务，保留旧同步API兼容；Vue改为先受理、后查询，提供本人任务列表、取消、人工重试和草稿重建。解析仍仅支持本机私有UTF-8 TXT/Markdown，不包含向量索引、模型或MCP调用。

## 3. 为什么用此方法，替代方案是什么

继续复用MySQL及Spring事务：当前文件上限1MiB、纯文字解析、两执行槽，另引MQ或Spring Batch会增加部署、迁移与调度学习成本。本轮曾检索GitHub的成熟任务恢复方向，但检索工具未返回可核验正文；没有移植开源实现，也不声称已核实具体框架API。不因检索不通而添加依赖。

仅用`@Async`/内存Future无法在重启后恢复受理状态。任务表让浏览器查询权威状态，gate唯一行只串行化短受理事务，用于跨成员/节点原子计数；解析原件时不持有gate锁。它是轻负载的直接方案，未来可能成为受理热点，需要实际MySQL压测后再评估分区配额或专用队列。

本地解析可以按租约恢复，因为原件不可变、SHA-256复核、片段有版本唯一索引且最终提交有事务栅栏。**不能把此自动恢复直接复制到模型调用、付款或其他副作用工具**：这些行为可能已经发生、结果未知，再执行会重复计费或产生交易。

## 4. 代码和数据如何流转

入口基础路径：`/api/enterprises/{enterprise}/knowledge-spaces/{space}/documents/{document}/versions/{version}/ingest-jobs`。

| 请求 | 输入/输出与异常 |
|---|---|
| POST 基础路径 | `{requestId: 小写UUID, expectedRevision: 正整数, action: PARSE或REBUILD}` → `Result<Job>`；400参数错、404无权/他人编号、409换参/修订变化/同版本在途、503满载 |
| GET 基础路径 | 本人同版本最近10项任务；维护权校验，不是企业全部人员任务监控 |
| GET `/{id}` | 查本人原UUID；不存在或跨范围统一404，可在文档删除后核对本人终态，但仍须空间维护权 |
| POST `/{id}/cancel` | 不覆盖已有终态，返回原任务当前状态；取消与成功竞态以数据库提交先后为准 |

例如：修订1的草稿版本12，提交UUID请求A、PARSE → QUEUED；后台抢占后RUNNING/attempts=1 → 事务写片段并递增文档修订为2，成功终态SUCCEEDED与这些写入同事务提交。重复A仍返回原任务，换动作/修订复用A返回409。另一UUID对就绪草稿做PARSE只复用片段，不再次递增修订；显式REBUILD会在同事务替换片段并递增修订。上述编号为说明用例，测试使用隔离库动态编号，不是开发库操作记录。

受理先重新校验账号/企业成员和空间维护权，再锁gate、文档并绑定修订/不可变版本；相同UUID只允许原提交者、同企业/空间/文档/版本、同修订与动作。后台重建认证身份，再走原文档授权入口；读取原件之后写片段前再次核权，取消/超时也不能靠旧身份快照绕过。

任务状态：`QUEUED → RUNNING → SUCCEEDED/FAILED`；QUEUED/RUNNING可转CANCELLED或TIMED_OUT。15秒租约过期且首次30秒总截止仍有余额时，最多恢复到第2次；第二次仍失去租约转RECOVERY_EXHAUSTED，总截止优先转TOTAL_TIMEOUT。业务失败不自动重试，人工重试先刷新修订、换新请求UUID；未知提交先核对原UUID，不能直接创建新任务。

`KnowledgeDocumentService.parseWithin`沿用两段事务：第一段核验草稿及revision，原件读取/解析在事务外；第二段最多每批100片段，清理与插入、READY和修订递增原子提交。`complete`条件更新必须仍为RUNNING、令牌匹配且租约/总截止有效，否则抛异常使片段事务回滚。旧worker即便仍持有内存数据，也不能覆盖新租约或取消终态。

## 5. 边界、故障和优化代价

| 场景 | 当前行为及限制 |
|---|---|
| 文件空/非法UTF-8/控制字符/过大 | 沿用上传和解析校验；安全INVALID_TEXT等分类，不记录原文、路径或供应商正文 |
| 同UUID并发/换参/他人UUID | gate内读取核对及主键唯一；同参复用，换参409，他人404，不返回他人任务 |
| 容量 | 全库最多64在途、每企业成员2个、同版本1个；每节点2物理worker，无内存排队，候选扫描最多16项 |
| 超时 | 受理起30秒，排队和恢复都扣同一余额；解析器已有5秒，片段事务10秒，受理等短事务5秒；HTTP沿用10秒等待 |
| 重启/崩溃 | QUEUED保持；RUNNING待租约到期最多恢复一次，已提交成功不重放。未实际杀进程实库演练，不称“已验证所有崩溃点” |
| 取消/过期/旧worker迟到 | 不依赖中断杀线程，最终CAS栅栏拒绝提交；取消不能撤销已经提交的成功片段 |
| 停机 | 关闭调度/线程池，事务回调检查停机与中断；未完成租约留新节点在原截止内恢复 |
| 部分片段写失败 | 全片段事务回滚；不能留下半套READY。任务记录安全失败供人工处理 |
| 重建失败 | READY草稿的旧片段、状态、revision保留；成功才替换。发布版拒绝重建，应上传新草稿版本 |
| 撤权/认证失效/版本变化 | 执行和提交前重核权、锁修订；不自动覆盖，不退回公开搜索或猜测成功 |
| 数据库结果未知 | 成功事务已提交时，后续FAILED条件更新不会覆盖；持久化失败只能待重连查询，不承诺异常代表未提交 |
| 浏览器刷新/断网 | 断开不新建后台任务；刷新后重新选文档版本，点“查看入库任务”；自动查询最多40秒，错误后人工刷新，不无限轮询 |

30秒是**逻辑提交与状态时限**，不是OS强杀线程的保证。阻塞磁盘/JDBC、数据库失联时仍可能无法及时返回终态；恢复后按持久截止收敛，旧任务不得写入。租约依赖节点时钟，生产需时钟同步、数据库驱动超时和磁盘故障演练，现有测试不证明硬实时退出。多节点每节点两槽，总物理执行数会随节点数增加；gate限制在途数，并非集群只运行两项。

后续优化必须以测量为前提：①gate锁等待明显再做分片容量/队列；②终态增长需先定企业留存和审计政策，再按索引分批归档；③解析格式/文件大小扩大时再引分阶段检查点、心跳续租或任务框架；④轮询读放大时评估退避/SSE通知，但数据库仍是恢复依据；⑤生产多节点需MySQL锁、时钟偏移、死锁/未知提交和目录共享测试。本轮均未实施，不以这些规划宣称生产容量。

**知识点/服务**：RAG的解析、重叠切分、片段来源定位及版本索引前置；Spring TransactionTemplate事务；MySQL行锁/唯一索引/条件更新；幂等键、租约和fencing token（隔离失去租约的旧执行者）；线程池有界背压；Vue状态机与有限轮询；Session/CSRF与服务端资源授权。没有使用MCP、向量服务、Redis或MQ。
