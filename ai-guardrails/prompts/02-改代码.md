# 提示词模板 02 · 改代码

> **用法**：每次让 AI 改代码时用。核心是**限定范围**。

---

## 模板 A：改单个文件（最常用）

```markdown
## 任务
在 `src/graph/nodes/rewrite.py` 里增加"多查询扩展"逻辑：
让改写节点生成 2-3 个不同角度的搜索查询。

## 限制
- ✅ 只改这一个文件
- ✅ 只做这个功能
- ❌ 不要顺手重构其他部分
- ❌ 不要调整代码风格
- ❌ 不要重写整个文件（先 Read，再 Edit 精确修改）

## 改完请报告
1. 改了哪几行
2. 为什么这么改
3. 有没有影响其他文件

⚠️ 改之前先 Read 这个文件。
```

---

## 模板 B：改多个文件（要分批）

```markdown
## 任务
把"Tavily 搜索"改成"支持多搜索源"（Tavily + 博查）。

## 我预计涉及的文件
1. `src/mcp/servers/tavily_server.py`
2. `src/graph/nodes/search.py`
3. `config/settings.py`

## ⚠️ 分批执行
请**一次只改一个文件**，每改完一个就停下来告诉我，等我确认后再改下一个。

不要一次性改完三个文件。

## 开始
先 Read 第一个文件，告诉我你的改动计划，**等我确认后再动手**。
```

> ⚠️ **涉及 3 个以上文件时，一定要求分批**。
> 一次性改太多，出错时你无法定位是哪个改动引入的。

---

## 模板 C：新增功能（要新建文件）

```markdown
## 任务
新增一个"检索结果缓存"模块。

## 计划
- 新建文件：`src/retrieval/cache.py`
- 不修改任何已有文件（先独立实现，测试通过后再接入）

## 要求
- 用 Redis 做缓存
- 提供 get / set 两个方法
- 有 TTL 参数
- 类型注解完整，注释用中文

## 请先
1. 告诉我你打算怎么写（接口设计、关键函数）
2. **等我确认后再创建文件**

⚠️ 这一步只出方案，不要创建文件。
```

> 💡 **"先出方案，确认后动手"** 能避免大量返工。
> 尤其是新建文件——**方案错了，写完就是白写**。

---

## 模板 D：改动有风险时（先备份）

```markdown
## 任务
重构 `src/main.py` 里的 SSE 事件生成逻辑。

## ⚠️ 这个改动有风险
这个文件有 400 行，涉及多个接口，改错了影响面大。

## 请按这个顺序做
1. 先告诉我 `git status` 的结果
2. 如果工作区不干净，**先提醒我提交**
3. 告诉我你打算改哪几行、怎么改
4. **等我确认后再动手**

⚠️ 如果我的工作区不干净，**不要动手**，先让我提交。
```

---

## 通用要素（每个模板都该有）

| 要素 | 作用 |
|---|---|
| **明确任务** | 说清要做什么 |
| **限制范围** | ✅ 只改哪个文件 ❌ 不要改哪些 |
| **禁止事项** | 明确列出不许做的 |
| **报告要求** | 改完要说清改了什么 |
| **⚠️ 先读文件** | 防止基于过时内容操作 |
| **⚠️ 先确认** | 高风险改动要等确认 |

---

## ❌ 反例（不要这样问）

```markdown
❌ "帮我优化一下这个项目"

问题：
- 没说什么算"优化"
- 没限定范围 → AI 可能改 20 个文件
- 没有禁止事项 → AI 可能顺手重构
```

```markdown
❌ "这个文件有问题，你看着改"

问题：
- "有问题"太模糊
- "看着改" = 授权它自由发挥
- 结果：改动范围不可控
```

```markdown
❌ "把所有的 Python 文件都格式化一下"

问题：
- 批量操作
- 会让所有文件的 diff 变成"全部改动"
- 你现在没法 review 任何东西
```

---

## ✅ 好问题的特征

| 特征 | 例 |
|---|---|
| **具体** | "在第 42 行后加一个函数" |
| **限定范围** | "只改这一个文件" |
| **说明为什么** | "因为多查询会产生重复 URL" |
| **给出验收标准** | "改完后 `pytest tests/test_rewrite.py` 应该通过" |
| **要求先报告** | "先告诉我方案，确认后再改" |
